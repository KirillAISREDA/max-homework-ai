# Деплой бота (VPS, Docker)

Бот работает в контейнере на VPS `193.247.73.243` (рядом — Redis для состояния диалогов) (Ubuntu 22.04, Docker 29, Compose v5),
каталог `/opt/max-homework-ai`. Режим — long polling: бот сам ходит к MAX и GigaChat,
входящих портов нет, Caddy/webhook не нужны. VPS общий с другими проектами (~25 контейнеров).

**Один поллер на токен.** Пока контейнер на VPS жив, не запускать `hwcheck bot` локально:
два поллера с одним `MAX_TOKEN` делят апдейты между собой.

## Что где

| Что | Где |
|---|---|
| Код | `/opt/max-homework-ai` — git-клон `main` + `.env` (не в git) |
| Контейнер | `homework-bot`, образ `max-homework-ai-bot`, `restart: unless-stopped`, лимит 1 ГБ |
| Состояние диалогов | контейнер `homework-redis` (`redis:8-alpine`, AOF, том `redis-data`, без портов), ключи `fsm:<хэш chat_id>` с TTL 24 ч |
| Журнал событий / marker | `/opt/max-homework-ai/var/` (том, переживает пересборку) |
| Фото домашек | `/opt/max-homework-ai/var/photos/<дата UTC>/<хэш user>-<id>.jpg`, удаляются через 30 дней (`PHOTOS_TTL_DAYS`); ключ фото — поле `photo` в `vision_recognized`/`photo_failed` |
| Кэш солвера | `/opt/max-homework-ai/.cache/solver/` (том) |
| Логи | `var/bot.log` (ротация 5 МБ × 3, переживает пересборку) и `docker compose logs -f` (только текущий контейнер) |
| Health | marker обновляется после каждого GET /updates; «unhealthy» = нет записи 5 минут (бот завис или опрос стоит из-за перегрузки — см. «Параллельная обработка апдейтов») |
| Остановка | `docker compose stop`: SIGTERM → бот перестаёт принимать апдейты, дообрабатывает принятые (до `SHUTDOWN_TIMEOUT_S` = 100 с) и выходит (grace 150 с); простаивающий long poll отменяется сразу |

Файлы деплоя в репозитории: `Dockerfile`, `.dockerignore`, `docker-compose.yml`.

## Первый запуск на чистом хосте

```bash
git clone https://github.com/KirillAISREDA/max-homework-ai.git /opt/max-homework-ai
cd /opt/max-homework-ai
cp .env.example .env && nano .env            # GIGACHAT_CREDENTIALS, GIGACHAT_SCOPE, MAX_TOKEN, ENVIRONMENT
mkdir -p var .cache && chown -R 1000:1000 var .cache   # контейнер работает от uid 1000
docker compose up -d --build
```

Если каталоги `var/` и `.cache/` создаст сам Docker, они будут от root, и бот не сможет писать
marker/журнал/кэш (в логах — PermissionError, health — unhealthy). Лечится тем же `chown`.

## PostgreSQL и ключи id (онбординг, этап 1)

С этапа 1 онбординга compose требует `POSTGRES_PASSWORD` в `.env`, а бот хэширует id через `ID_HASH_KEY`
(HMAC) и проверяет `USER_ID_KEY` при старте. Первая выкатка — один раз:

```bash
# на VPS, в /opt/max-homework-ai; перед этим — нет событий за 10 минут
git pull
cp .env .env.bak-$(date +%F) && chmod 600 .env.bak-*
docker build -t max-homework-ai-bot .
docker run --rm max-homework-ai-bot python -m hwcheck keys >> .env   # секреты сразу в .env, не на экран
grep -o '^[A-Z_]*=' .env                                               # проверить только имена
mkdir -p var/backups && chmod 700 var/backups   # дампы с данными детей — только root
docker compose up -d postgres pgbackup bot                             # Redis не трогаем
docker compose logs --tail 20 bot                                      # «migrations applied: 001_onboarding.sql»
```

Копию `ID_HASH_KEY`, `USER_ID_KEY`, `POSTGRES_PASSWORD` Кирилл хранит вне VPS: без `USER_ID_KEY` бот не
сможет писать пользователям, без `ID_HASH_KEY` — найти их. Переход на HMAC один раз сбрасывает открытые
разборы (ключи Redis `fsm:<хэш>` меняются); тестеры из старого `TEST_USERS` узнаются и по прежнему хэшу.

```bash
docker exec homework-postgres psql -U homework -c '\dt'                   # таблицы онбординга
docker exec homework-postgres psql -U homework -c 'SELECT * FROM schema_migrations'
ls -la var/backups                                                       # ежедневные дампы, хранение 7 дней
```

## Онбординг: включение и аварийный выключатель (этап 2)

Миграция `002_children.sql` применяется при старте бота и пересоздаёт пустые таблицы профилей и согласий;
если в них уже есть данные — бот не стартует (в логе `002_children: в student_profiles…`). Перед выкаткой
миграции — проверка, что таблицы пусты:

```bash
docker exec homework-postgres psql -U homework -c 'SELECT (SELECT count(*) FROM student_profiles) sp, (SELECT count(*) FROM consents) c, (SELECT count(*) FROM homeworks) h'
```

Все три числа — нули, иначе миграция 002 не применится и бот уйдёт в перезапуски.

Включить:

```bash
# на VPS, в /opt/max-homework-ai; перед этим — нет событий за 10 минут
# printf, а не echo: если .env не кончается переводом строки, echo склеил бы строки
grep -q '^ONBOARDING_REQUIRED=' .env \
  && sed -i 's/^ONBOARDING_REQUIRED=.*/ONBOARDING_REQUIRED=true/' .env \
  || printf '\nONBOARDING_REQUIRED=true\n' >> .env
docker compose up -d --force-recreate bot        # env_file перечитывается только при пересоздании
docker compose logs --tail 20 bot                # «onboarding: required»
```

С запуска для реальных семей (01.10.2026) флаг `ONBOARDING_REQUIRED=true` в prod включён постоянно:
оператор в политике назван (действует v2: передача фото сторонней модели), отзыв согласия и удаление данных — по письму оператору, вручную
(«Удаление данных по запросу» ниже); меню отзыва (этап 3) и вычитка политики юристом — в работе.

Выключить (поломка онбординга мешает проверке): то же с `ONBOARDING_REQUIRED=false`, в логе
`onboarding: off` (в prod ещё предупреждение «фото проверяются без согласия родителя»). Профили и согласия
в базе остаются.

Сбросить тестовый аккаунт для повторного прохода (хэш — поле `user` в `var/events.jsonl`). Команды одного
`psql -c` выполняются одной транзакцией; порядок важен — дети 1–4 удаляются раньше родителя:

```bash
docker exec homework-postgres psql -U homework -c "
  UPDATE consents SET revoked_at = now() WHERE revoked_at IS NULL
    AND (parent_hash = '<хэш>' OR student_hash = '<хэш>');
  DELETE FROM student_profiles WHERE user_id IS NULL
    AND parent_user_id = (SELECT id FROM users WHERE max_user_hash = '<хэш>');
  DELETE FROM users WHERE max_user_hash = '<хэш>';
  DELETE FROM login_attempts WHERE user_hash = '<хэш>';
  DELETE FROM subject_waitlist WHERE user_hash = '<хэш>';"
docker exec homework-redis redis-cli DEL 'onb:<хэш>'
```

- Сброс родителя: профили его детей 1–4 удаляются, а у ребёнка 5–9 класса со своим MAX связь с родителем
  обнуляется (профиль остаётся, согласие отозвано) — для чистого повтора сбрасывать оба хэша, родителя и ребёнка.
- Записи согласий не удаляются, а остаются с `revoked_at` — это юридическая запись. Без отзыва ребёнок остался
  бы «с согласием», а связка с другим родителем упала бы на `consents_one_active`.
- Это сброс тестового аккаунта; удаление данных пользователя по его запросу — ниже.

### Удаление данных по запросу

Политика (п. 7) обещает: по письму оператору профиль, результаты проверок и фотографии удаляются,
вторая сторона получает уведомление. Пока нет меню отзыва (этап 3 онбординга), оператор делает это
вручную. Срок — не дольше 10 рабочих дней с получения письма.

1. **Убедиться, что пишет владелец аккаунта.** По письму аккаунт MAX не найти: бот не хранит ни
   имени, ни почты. Попросить в ответном письме отправить боту любое сообщение и назвать время
   отправки с точностью до минуты; найти это сообщение в журнале и взять его хэш:

   ```bash
   cd /opt/max-homework-ai
   grep '"type": "message_received"' var/events.jsonl | tail -20   # ts — время в секундах UTC
   ```

2. **Решить, чьи данные удалять.** Пишет родитель — удаляются его аккаунт и дети 1–4 класса, у
   ребёнка 5–9 класса со своим MAX согласие отзывается, и проверка для него закрывается; если
   родитель просит удалить и данные ребёнка 5–9 класса — удалить и его хэш (он есть в `consents`
   рядом с хэшем родителя).

3. **Проверить, что бот свободен** (правило прода — события за 10 минут), и удалить:

   ```bash
   docker exec homework-postgres psql -U homework -c "
     UPDATE consents SET revoked_at = now() WHERE revoked_at IS NULL
       AND (parent_hash = '<хэш>' OR student_hash = '<хэш>');
     DELETE FROM student_profiles WHERE user_id IS NULL
       AND parent_user_id = (SELECT id FROM users WHERE max_user_hash = '<хэш>');
     DELETE FROM users WHERE max_user_hash = '<хэш>';
     DELETE FROM findings WHERE user_hash = '<хэш>';
     DELETE FROM login_attempts WHERE user_hash = '<хэш>';
     DELETE FROM subject_waitlist WHERE user_hash = '<хэш>';"
   docker exec homework-redis redis-cli DEL 'onb:<хэш>'
   find var/photos -name '<хэш>-*' -print -delete
   ```

   Вместе с аккаунтом по внешним ключам удаляются его профиль, настройки уведомлений, приглашения,
   записи `homeworks` и отметки отчёта раз в неделю (`weekly_reports`). Состояние диалога в Redis (`fsm:*`) хранится по чату, а не по пользователю,
   и само истекает через 24 часа.

4. **Что остаётся и почему** (политика, п. 6): запись о согласии с отметкой отзыва — подтверждение
   законной обработки; журнал обращений `var/events.jsonl` — в нём только хэш, без фото и текста
   заданий; резервные копии базы — 7 дней, дольше не хранятся.

5. **Сообщить второй стороне** (родителю или ребёнку 5–9 класса), что согласие отозвано и данные
   удалены, и ответить на письмо. Если вторую сторону удалили тем же запросом, сообщать некому.

6. **Записать в `HISTORY.md`** дату запроса и дату удаления — без хэша и без адреса почты.

## Отчёт родителю по запросу

Кнопка «📈 Отчёт о прогрессе» — у родителя под списком детей (когда есть хотя бы один ребёнок с
согласием) и второй строкой под каждым итогом проверки. По нажатию бот одним сообщением отвечает в
тот же чат. Настроек у отчёта по кнопке нет — он включён вместе с онбордингом
(`ONBOARDING_REQUIRED=true`) и работает всегда: ни настройка рассылки `WEEKLY_REPORT`, ни
выключатель родителя «Не присылать по воскресеньям» на него не влияют. Рассылка по расписанию —
раздел «Отчёт родителю раз в неделю» ниже.

- **Период** — последние 7 календарных дней по московскому времени, включая сегодня: часовой пояс
  семьи неизвестен. Нажатие 29 сентября в 23:59 мск даёт «23–29 сентября», в 00:00 — уже
  «24–30 сентября».
- **Что в отчёте:** блок на каждого ребёнка с действующим согласием — «Ребёнок (7 класс)», как в
  итогах после проверки; по каждому предмету — сколько домашек и заданий, сколько верно, с
  ошибкой (и сколько ошибок разобрано с подсказками), «стоит перепроверить» и без оценки. Строки
  с нулём не показываются. Проверок не было — так и написано.
- **Чего в отчёте нет:** имени ребёнка, текста заданий, ответов, номеров заданий и фото; сравнения
  детей между собой, рейтингов, серий и призов. Ошибок по видам тоже нет.
- **Источник** — только таблица `homeworks` (счётчики проверок). Отчёт собирает код, модель не
  вызывается: на стоимость и на журнал `llm_call` он не влияет.
- **Чьи дети.** Отчёт — всегда о детях нажавшего: в кнопке нет ничьих id (`ob:report`), кнопка с
  любым аргументом (`ob:report:…`) отчёта не даёт. Ученик и посторонний по этой кнопке видят
  свой текущий шаг. Отчёт получает и родитель ребёнка 1–4 класса, который присылает фото сам.
- **Отозванное согласие:** ребёнок из отчёта пропадает, даже если проверки за период были.
- Отчёт не длиннее одного сообщения MAX (4000 знаков): что не поместилось, отбрасывается целыми
  блоками детей, в конце — «Не показано детей: N».
- **Повторное нажатие** раньше чем через 20 секунд после отправленного отчёта отчёт не собирает и
  ничего не отвечает: отчёт уже выше в чате. Пауза — у каждого родителя своя, после сбоя её нет.

События журнала (`var/events.jsonl`); у событий отчёта по кнопке — `component: report` и
`user_initiated: true`:

| Событие | Поля | Когда |
|---|---|---|
| `button_pressed` | `payload: ob:report` | кнопка нажата (кем угодно) |
| `parent_report_sent` | `kind: on_request`, `children` — детей в отчёте, `homeworks` — проверок в отчёте, `empty` — проверок не было | отчёт отправлен родителю |
| `parent_report_failed` | `kind: on_request`, `error` — класс исключения | отчёт не собран или не отправлен; родитель видит «Не получилось собрать отчёт» |
| `parent_report_skipped` | `kind: on_request`, `reason: cooldown` | повторное нажатие раньше паузы: отчёт не собирался |

`button_pressed` пишет маршрутизатор онбординга, поля `component` у него нет. В событиях отчёта —
обезличенный id нажавшего (`user`) и счётчики: ни id профилей, ни id MAX, ни текста исключения.

```bash
cd /opt/max-homework-ai
grep -c '"type": "parent_report_sent"' var/events.jsonl      # сколько отчётов отправлено
grep '"type": "parent_report_failed"' var/events.jsonl | tail  # сбои: поле error
grep 'parent report failed' var/bot.log | tail
```

## Отчёт родителю раз в неделю

Тот же отчёт бот присылает сам — раз в неделю, по умолчанию в воскресенье в 18:00 по Москве.
Рассылка — задача внутри процесса бота: отдельного контейнера, cron и очереди у неё нет, MAX она
не опрашивает и marker не трогает. Модель не вызывается: отчёт собирает код из таблицы
`homeworks`.

По умолчанию рассылка **выключена**. Ей нужен онбординг (`ONBOARDING_REQUIRED=true`, база и
ключи id). Миграция `005_weekly_report.sql` применяется при старте бота независимо от настройки:
она добавляет колонку `parent_settings.weekly_report` (у всех родителей — `true`) и таблицу
`weekly_reports`.

Включить:

```bash
# на VPS, в /opt/max-homework-ai; перед этим — нет событий за 10 минут
grep -q '^WEEKLY_REPORT=' .env \
  && sed -i 's/^WEEKLY_REPORT=.*/WEEKLY_REPORT=true/' .env \
  || printf '\nWEEKLY_REPORT=true\n' >> .env
docker compose up -d --force-recreate bot        # env_file перечитывается только при пересоздании
docker compose logs --tail 30 bot | grep 'weekly report'
```

В логе при старте — одна строка:

| Строка | Что значит |
|---|---|
| `weekly report: off` | рассылка выключена настройкой |
| `weekly report: on, next slot 2026-10-04 18:00 MSK` | включена; следующая рассылка — в этот час |
| `…, catching up 2026-10-04 18:00 MSK` | бот стартовал в окне отправки: кому отчёт этой недели не ушёл, уйдёт сейчас (`after quiet hours` — утром) |
| `weekly report: off — WEEKLY_REPORT=true, но онбординг выключен или нет базы` | предупреждение: настройка включена, а рассылки нет |

Выключить — то же с `WEEKLY_REPORT=false`. Отметки недель и выключатели родителей в базе остаются,
отчёт по кнопке работает.

### Настройки

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `WEEKLY_REPORT` | `false` | рассылка включена |
| `WEEKLY_REPORT_WEEKDAY` | `6` | день недели: 0 — понедельник, 6 — воскресенье |
| `WEEKLY_REPORT_HOUR` | `18` | час по московскому времени, от 9 до 21 |
| `WEEKLY_REPORT_PAUSE_S` | `0.5` | пауза между родителями, секунды |

Час в тихие часы (с 22 до 8) бот не принимает и не стартует: `WEEKLY_REPORT_HOUR=23: с 22 до 9
часов по Москве бот родителям не пишет — задайте час с 9 до 21`. День или час вне границ — ошибка
настроек при старте (в тексте — `weekly_report_weekday` или `weekly_report_hour`). Проверка идёт и
при выключенной рассылке. Окно догоняющей отправки (27 часов), тихие часы (22:00–09:00), срок
одной отправки (20 с) и шаг проверки (60 с) — в коде, `src/hwcheck/bot/report_schedule.py`.

После смены дня или часа надписи на выключателе меняются сами («Не присылать по средам»), а
неделя отчёта считается от нового слота: первая неделя после смены пересечётся с последней до
неё или оставит между ними промежуток.

### Что получает родитель

- **Кто получает:** аккаунт с ролью «родитель», у которого есть хотя бы один ребёнок с
  действующим согласием, данным до часа рассылки, — по любой версии политики. В том числе
  родитель ребёнка 1–4 класса, который присылает фото сам. Согласие дано после часа рассылки —
  первый отчёт придёт через неделю.
- **Неделя** — 7 суток до часа рассылки, сам час в неделю не входит: каждая домашка попадает
  ровно в один отчёт. Рассылка 4 октября в 18:00 — это домашки с 27 сентября 18:00 до 4 октября
  18:00, в заголовке — «📈 Отчёт за неделю: 28 сентября – 4 октября». День прошлой рассылки в
  заголовок не входит, хотя его вечер в неделю входит: иначе одна дата закрывала бы один отчёт и
  открывала следующий. Домашка, проверенная в воскресенье после 18:00, попадает в отчёт
  следующей недели. Отчёт по кнопке считает иначе — 7 календарных дней, включая сегодня, —
  поэтому числа в двух отчётах могут не совпасть.
- **Экран согласия** обещает «раз в неделю или по вашему запросу» только при включённой
  рассылке; при выключенной — «по вашему запросу».
- **Одно сообщение родителю**, блок на каждого ребёнка с действующим согласием — те же блоки,
  что в отчёте по кнопке. Обычный текст, без разметки.
- **Неделя без домашек.** Неделей раньше домашки были — уходит одно короткое сообщение: «На этой
  неделе домашку на проверку не присылали.» Не было и неделей раньше — не уходит ничего, неделя
  отмечается `skipped`. Семья, которая ботом не пользуется, получает «пустой» отчёт не больше
  одного раза. Домашки ребёнка с отозванным согласием не считаются.
- **Под отчётом — одна кнопка**, выключатель «Не присылать по воскресеньям». Кнопки «📈 Отчёт о
  прогрессе» под ним нет.

### Выключатель родителя

Кнопка под отчётом — «Не присылать по воскресеньям» (`ob:weekly:off`); бот подтверждает и
показывает «Присылать по воскресеньям» (`ob:weekly:on`). День в надписи — из настройки
`WEEKLY_REPORT_WEEKDAY`.

- Выключатель меняет только нажавший и только себе: в кнопке нет ничьих id. Принимаются только
  `on` и `off`; `ob:weekly`, `ob:weekly:`, `ob:weekly:off:1` и любой другой аргумент, а также
  нажатие ученика или постороннего показывают нажавшему его текущий шаг.
- Он не зависит от «Не присылать итоги» (`notify_mode`): это другая колонка той же строки
  `parent_settings`, запись одного не сбрасывает другой.
- Отчёт по кнопке работает и с выключенной рассылкой.
- Кнопка работает и при `WEEKLY_REPORT=false`: выбор родителя запоминается до включения рассылки.

Посмотреть, сколько родителей выключили рассылку:

```bash
docker exec homework-postgres psql -U homework -c \
  "SELECT count(*) FROM parent_settings WHERE NOT weekly_report"
```

### Догоняющая отправка и тихие часы

Раз в минуту (первый раз — сразу при старте) бот смотрит, наступил ли час рассылки, и пишет тем,
у кого нет отметки этой недели. Между родителями — пауза `WEEKLY_REPORT_PAUSE_S`.

- **Бот лежал в час рассылки** — отчёт уйдёт после старта, но не позже чем через 27 часов после
  часа рассылки (воскресенье 18:00 → до понедельника 21:00). Отчёт — за ту же неделю, что ушёл
  бы вовремя.
- **С 22:00 до 09:00 по Москве** бот родителям не пишет: что не ушло в воскресенье до 22:00,
  уйдёт в понедельник с 09:00. Ночь может начаться и посреди рассылки — она остановится и
  продолжится утром.
- **Окно прошло** — неделя пропущена: отчёт за неё не придёт, следующая неделя идёт как обычно.
  В журнале — одно событие `weekly_slot_missed`. При первом включении рассылки посреди недели
  оно тоже запишется — за час рассылки, который прошёл до включения; после рестарта бота в
  пропущенную неделю — ещё раз.
- **Повторов нет.** Отчёт не дошёл (родитель заблокировал бота, MAX ответил ошибкой или не
  ответил за 20 секунд) — отметка `failed`, событие, следующий родитель. Этот родитель получит
  отчёт через неделю или по кнопке.

### Не больше одного раза

Отметка недели (`weekly_reports`: родитель и час рассылки) ставится **до** отправки — как marker
опроса MAX сохраняется до обработки. После рестарта бот пропускает всех, у кого отметка есть, и
отчёт не уходит второй раз. То же — если запущены два процесса бота: отметку ставит один.

| Статус | Что значит |
|---|---|
| `sent` | отчёт отправлен (в том числе короткое сообщение о неделе без домашек) |
| `skipped` | писать не о чем: домашек не было две недели подряд, или согласие отозвано перед самой отправкой |
| `failed` | отчёт не собран или не отправлен; повтора не будет |
| `sending` | отметка поставлена, итог не записан |

Строка, которая осталась в `sending`, — след остановки или сбоя посреди отправки: процесс упал
или был остановлен между отметкой и отправкой (отчёт потерян), либо отчёт ушёл, а записать итог
не удалось (база не ответила). Узнать, какой из двух случаев, по отметке нельзя — в журнале во
втором случае есть `parent_report_sent` и следом `weekly_loop_failed`. Повторно такой отчёт бот
не отправит; править строки руками не нужно.

Если отчёт всё же надо дослать — удалить строку, пока не кончилось окно отправки. **Удаление
снимает защиту от повтора:** если отчёт на самом деле ушёл (второй случай), родитель получит его
второй раз. Сначала проверить журнал: есть `parent_report_sent` с `kind: weekly` за этот вечер
и следом `weekly_loop_failed` — строки не трогать.

Удалять — по одному родителю, а не всю неделю разом: у других родителей с той же отметкой отчёт
мог уйти.

```bash
grep -E '"type": "(parent_report_sent|weekly_loop_failed)"' var/events.jsonl | tail -20
docker exec homework-postgres psql -U homework -c \
  "SELECT parent_user_id, claimed_at FROM weekly_reports
   WHERE status = 'sending' AND period_end = '2026-10-04 18:00+03'"
docker exec homework-postgres psql -U homework -c \
  "DELETE FROM weekly_reports WHERE status = 'sending'
   AND period_end = '2026-10-04 18:00+03' AND parent_user_id = <id из запроса выше>"
```

### Остановка бота

По SIGTERM рассылка новых отчётов не начинает, начатый доводит до конца и выходит; сон между
проверками остановка прерывает сразу. На это у неё 25 секунд от самой остановки — одновременно с
дообработкой апдейтов (`SHUTDOWN_TIMEOUT_S`), а не после неё; дальше рассылка отменяется, в логе —
`weekly report loop cancelled`. К `stop_grace_period` рассылка ничего не добавляет. Родители, до
которых очередь не дошла, остаются без отметки и получат отчёт после старта, если окно ещё
открыто.

Сбой рассылки бота не останавливает: исключение внутри проверки — событие `weekly_loop_failed` и
следующая проверка через минуту.

### События журнала

У всех — `component: report` и `user_initiated: false`, кроме `weekly_report_set`: его вызывает
нажатие.

| Событие | Поля | Когда |
|---|---|---|
| `parent_report_sent` | `kind: weekly`, `children`, `homeworks`, `empty` — домашек за неделю не было | отчёт отправлен |
| `parent_report_failed` | `kind: weekly`, `error` — класс исключения (`TimeoutError` — не уложился в 20 с) | отчёт не собран или не отправлен |
| `parent_report_skipped` | `kind: weekly`, `reason`: `empty` — домашек не было две недели подряд, `no_children` — детей с согласием не осталось | отчёт не отправлялся |
| `weekly_report_set` | `enabled` | родитель нажал выключатель |
| `weekly_loop_failed` | `error` — класс исключения | сбой проверки (база недоступна); поля `user` нет |
| `weekly_slot_missed` | — | окно отправки прошло, а не получившие отчёт остались; поля `user` нет |

В событиях отчёта — обезличенный id получателя (`user`) и счётчики: ни id профилей, ни id MAX, ни
текста исключения. Id MAX родителя расшифровывается в момент отправки и для записи события — в
журнал уходит только хэш. События тестеров (`TEST_USERS`) пишутся с `env=test`, как и в
остальном журнале. У каждого отчёта свой `trace_id`. Если id родителя не расшифровался
(сменили `USER_ID_KEY`), отметка — `failed`, а события нет: в логе `weekly report failed:
UserIdCipherError` и `parent_report_failed not written`.

```bash
# когда рассылка началась и сколько шла
```

## OCR-сервис

Контейнер `homework-ocr` — посимвольное распознавание рукописи для языков (спецификация каркаса §8),
движок `ReadingPipelineEngine`. Код — пакет `ocrsvc/` (`ocrsvc/Dockerfile`; имя `ocr` занято апстримным
пакетом ai-forever и затеняет его в `PYTHONPATH`, поэтому свой пакет называется иначе). Сервис compose —
`ocr`, образ `max-homework-ai-ocr`, контейнер `homework-ocr`; не стартует вместе с остальными по
умолчанию, только явно, через профиль `ocr`.

Сборка (клоны ai-forever + веса 165 МБ, ~5–10 мин):

```bash
docker compose --profile ocr build ocr
```

Запуск — только когда на VPS свободно достаточно памяти (лимит контейнера 2 ГБ + запас на пик и на
соседние контейнеры):

```bash
free -m                                    # available ≥ 2,5 ГБ
docker compose --profile ocr up -d ocr
docker exec homework-ocr python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8080/health').read())"
```

Лимит памяти сервиса — **`2 ГБ`** (было `3 ГБ` до follow-up спайка 17.09 —
`docs/research/2026-09-17-readingpipeline-memory.md`): пик на реальных фото — **1,46 ГБ**, без `torch`
в образе и с выключенными `enable_cpu_mem_arena`/`enable_mem_pattern` у сессий onnxruntime. Cloud.ru или
апгрейд VPS для этого больше не нужны. `restart: on-failure:3` — сбой инициализации движка (нет весов,
битый конфиг, OOM) не должен крутить контейнер вечно на общем VPS: каждая попытка заново грузит
~1,4 ГБ весов.

Дымовой тест — реальное фото тетради из `var/photos` (то, что уже прошло через бота и пережато):

```bash
f=$(ls var/photos/*/*.webp | head -1)
docker run --rm --network max-homework-ai_default -v $PWD/var/photos:/p:ro python:3.12-slim \
  python -c "import urllib.request; r=urllib.request.Request('http://ocr:8080/recognize', data=open('/p/${f#var/photos/}','rb').read(), headers={'Content-Type':'image/webp'}); print(urllib.request.urlopen(r, timeout=90).read()[:600])"
docker stats --no-stream homework-ocr        # ожидаемо ~1,3–1,5 ГБ
```

Ожидаемо: `words` непустой, `seconds` 5–15.

Включение в боте — `OCR_URL=http://ocr:8080` в `.env` (сервис виден боту по имени в сети compose),
затем пересоздать бота, чтобы он подхватил переменную окружения:

```bash
docker compose up -d --build bot
```

Откат — если OCR не тянет память на общем VPS или не поднимается: остановить сервис и очистить
`OCR_URL`, бот тогда не падает, а отвечает ребёнку «не смог прочитать тетрадь» (событие `ocr_failed`
в `var/events.jsonl`):

```bash
docker compose stop ocr
sed -i 's/^OCR_URL=.*/OCR_URL=/' .env
docker compose up -d --build bot
```

Как для любого рестарта прод-контейнеров общего VPS — сначала нет событий за 10 минут (`tail
var/bot.log`, `tail var/events.jsonl`), Redis не трогать.

### Стенд русского

`hwcheck bench ru` (по эталонным кейсам `bench/golden_ru/`) нужно гонять против настоящего OCR, а не
фейка. `--ocr-url http://127.0.0.1:8080` (дефолт команды для локального запуска) на VPS с хоста не
достаёт: у `homework-ocr` нет портов наружу, только сеть compose. Практический способ — гонять стенд
изнутри той же сети, из одноразового контейнера бота:

```bash
docker compose --profile ocr up -d ocr
# фото кейсов — на VPS в /opt/max-homework-ai/data (скопировать заранее, каталог не в образе — .dockerignore)
docker compose run --rm -v "$PWD/data:/app/data:ro" bot \
  python -m hwcheck bench ru --ocr-url http://ocr:8080 --photos data \
  --out var/bench-russian-$(date +%F).md
```

Эталонные кейсы (`bench/golden_ru/`) лежат в образе (`COPY bench ./bench` в `Dockerfile`), а отчёт
пишется в `var/` — он смонтирован с хоста (как и `.cache/`): `--rm` уносит с собой всё, что
контейнер записал в свою файловую систему, поэтому `--out bench/reports/…` внутри контейнера
потерялся бы. Отчёт (`var/bench-russian-<дата>.md`) — точность и полнота кандидатов; на хосте его
кладут в `bench/reports/<дата>-russian.md` и коммитят:

```bash
cp var/bench-russian-$(date +%F).md bench/reports/$(date +%F)-russian.md
```

Прогон сохраняется в `.cache/bench/runs/russian.jsonl` — там текст слов из тетрадей детей; этот файл
**не должен уходить с VPS и не должен попадать в git** (уже в `.gitignore`/`.dockerignore` — не
выносить).

## Параллельная обработка апдейтов

Бот обрабатывает сообщения разных чатов одновременно, сообщения одного чата — строго по порядку
прихода (`bot/dispatch.py`). Опрос MAX обработки не ждёт: пока одной семье проверяется домашка
(30–60 с), кнопки и сообщения остальных принимаются и обрабатываются.

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `UPDATE_CONCURRENCY` | 8 | Сколько апдейтов обрабатывается одновременно. `1` — по одному в порядке прихода, как до выкатки диспетчера |
| `UPDATE_QUEUE_LIMIT` | 100 | Порог необработанных апдейтов (в очередях и в обработке). Достигнут — бот перестаёт опрашивать MAX, пока очередь не разгрузится до половины порога |
| `SHUTDOWN_TIMEOUT_S` | 100 | Срок дообработки принятых апдейтов при остановке, секунды. Должен быть меньше `stop_grace_period` (150 с в `docker-compose.yml`) |

Неверное значение (ноль, отрицательное) — бот не стартует, в ошибке имя настройки.

- **Проверки ограничены ещё и клиентами моделей.** GigaChat API — `GIGACHAT_CONCURRENCY` (1 на
  тарифе физлица), шлюз — `LLM_GATEWAY_CONCURRENCY` (8). Пока чтение фото идёт в GigaChat API,
  проверки разных семей встают в очередь к его одному потоку; кнопки, онбординг и шаги, идущие
  через шлюз, этой очереди не ждут.
- **Перегрузка.** При `UPDATE_QUEUE_LIMIT` необработанных апдейтов в `var/bot.log` —
  `updates backlog 100 >= 100: polling paused`, после разгрузки — `polling resumed after … s`.
  Апдейты в это время копятся на стороне MAX, а не в памяти бота. В памяти бывает до порога плюс
  один батч (100 апдейтов). Marker во время паузы не обновляется: пауза дольше 5 минут покажет
  контейнер как `unhealthy` — это сигнал перегрузки, сам контейнер от этого не перезапускается.
- **Остановка** (`docker compose stop`, пересборка при выкатке): опрос прекращается, принятые
  апдейты дообрабатываются — и начатые, и ждущие в очередях; в логе
  `stopping: N accepted updates to finish in 100 s`. Не уложились в срок — обработки отменяются:
  `shutdown timeout 100 s: N updates lost (K cancelled in progress, M never started)`. Потерянные
  апдейты MAX повторно не отдаст (marker сдвигается при получении батча): пользователь останется
  без ответа и напишет ещё раз. Поэтому перед рестартом — по-прежнему события за 10 минут.
- **База.** Пул PostgreSQL — 10 соединений, не меньше одновременных обработок; обработки берут
  соединение на время запроса. `UPDATE_CONCURRENCY` больше 10 — запросы ждут свободного
  соединения, а не падают.
- **Откат.** `UPDATE_CONCURRENCY=1` в `.env` и `docker compose up -d --force-recreate bot`.

При старте бот пишет пределы в лог: `updates: up to 8 at once, backlog limit 100, shutdown
timeout 100 s`.

## Нагрузочный тест

`python -m hwcheck.loadtest` подаёт боту поток сообщений виртуальных семей и пишет отчёт по
шагам нагрузки: время ответа, пропускная способность, очередь, вызовы модели, токены в минуту,
стоимость, пик памяти. У бота нет HTTP-входа, поэтому нагрузка идёт туда же, куда её подаёт
опрос MAX, — в диспетчер апдейтов. Модели, очередь и журнал вызовов настоящие; подменён только
мессенджер, состояние диалогов — в памяти процесса. База, Redis и журнал прод-бота не
затрагиваются.

```bash
cd /opt/max-homework-ai
mkdir -p var/loadtest/photos && chown -R 1000:1000 var/loadtest
# страницы — только открытый датасет (`data/photo_*`), не работы детей
docker run --rm --name homework-loadtest --memory 1g --cpus 1 \
  --env-file .env -v "$PWD/var/loadtest:/app/var/loadtest" max-homework-ai-bot \
  python -m hwcheck.loadtest --photos var/loadtest/photos \
  --steps "1:60,2:60,5:60,10:60" --out var/loadtest/report.md
```

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `--steps` | `1:60,2:60,5:60,10:60` | Шаги «сообщений в секунду : секунд» |
| `--concurrency` | `UPDATE_CONCURRENCY` | Одновременных обработок: поиск предела при других настройках |
| `--drain-timeout` | 300 | Сколько секунд после шага ждать ответов; что не дождались — «без ответа» |
| `--tutor-answers` | 2 | Ответов тьютору на каждый разбор |
| `--events` | `var/loadtest/events.jsonl` | Журнал теста (среда `loadtest`) |

- **Это деньги.** Проверка одной страницы — около 2 ₽ бюджета шлюза; шаги по умолчанию — до
  1 080 сообщений. Перед прогоном — остаток бюджета ключа.
- **Семья ведёт себя как живая:** присылает домашку, ждёт ответа, нажимает «Разобрать», отвечает
  тьютору, присылает следующую. Пока бот ей не ответил, она молчит — следующее сообщение потока
  приходит от новой семьи.
- **Фото читает модель прода** (`VISION_MODEL`): страницы теста — открытый датасет, согласие на
  них не нужно. Кэш эталонных решений выключен: страниц мало, с кэшем нагрузка была бы заниженной.
- **Шаги независимы.** Что бот не разобрал за `--drain-timeout`, отменяется и в замеры следующего
  шага не попадает.
- **VPS общий.** Контейнер теста — с пределами памяти и процессора, отдельно от бота; перед
  прогоном — события бота за 10 минут, как перед рестартом.

```bash
docker ps --filter name=homework                # статус и health бота и Redis

tail -50 var/bot.log                            # роли страниц, ошибки (переживает пересборку)
tail -5 var/events.jsonl                        # последние события пайплайна (trace_id связывает события апдейта)
docker exec homework-redis redis-cli --scan --pattern 'fsm:*' | wc -l   # открытые диалоги
du -sh var/photos                               # объём сохранённых фото
docker compose restart
```

Сводка вердиктов и причин «не уверен» (prod / test отдельно; причины пишутся с 14.09):

```bash
docker exec homework-bot python -m hwcheck report var/events.jsonl
```

Причины: `unreadable` — на странице «неразборчиво»; `ambiguous_equation` — корень сменился без явной связи;
`answer_unparseable` — ответ записан, но не разобран; `no_answer` — ответа нет и последняя строка не эталон;
`steps_unparseable` — не разобрана ни одна строка. Рядом `ref_status`: `no_condition`, `solver_failed`,
`ref_not_verified`, `ok`.

Разобрать спорную проверку: найти в `var/events.jsonl` событие `task_checked` с нужным вердиктом,
по его `trace_id` — `vision_recognized` с полем `photo`, открыть `var/photos/<photo>`.

## Журнал вызовов модели и стоимость

Каждый вызов GigaChat (в том числе упавший) — отдельное событие `llm_call` в `var/events.jsonl`.
События шагов (`vision_recognized`, `solver_call`, `tutor_reply`…) пишутся как раньше: они суммируют
шаг, а `llm_call` — единица счёта за токены и обращение по методике конкурса.

```json
{"ts": 1790588172.37, "env": "prod", "trace_id": "b0e1c091dc19499f", "type": "llm_call",
 "user": "8e215abebf11e7e4", "component": "llm", "user_initiated": false, "step": "solver",
 "prompt_version": "v1", "model": "GigaChat-2-Max", "kind": "chat", "tokens_in": 1480,
 "tokens_out": 212, "latency_ms": 4062, "status": "ok", "error": null}
```

| Поле | Значение |
|---|---|
| `step`, `prompt_version` | шаг пайплайна и версия его промпта — файл `prompts/<step>/<prompt_version>.md`; шаги: `vision`, `vision_structure`, `solver`, `classifier`, `tutor`, `generator`, `ru_page`, `ru_gaps`, `ru_orthogram`, `ru_tutor`; вызов вне шага — `unknown` и `null` |
| `model`, `kind` | модель из запроса; `chat` — текст, `vision` — фото (загрузка файла, запрос и удаление файла — один вызов) |
| `tokens_in`, `tokens_out` | токены запроса (уже без кэшированных) и ответа; у упавшего вызова — 0 |
| `latency_ms` | время вызова целиком, у упавшего — до ошибки |
| `status`, `error` | `ok` или `error`; `error` — имя класса исключения, без текста ошибки |
| `user`, `env`, `trace_id` | обезличенный автор апдейта, среда (`test` у тестеров из `TEST_USERS`) и трасса апдейта |

Текст промптов и ответов модели в журнал не пишется. Повтор при невалидном JSON — отдельное событие
того же шага; ответ солвера из кэша события не даёт (вызова модели нет). Если журнал не записался
(диск), вызов модели не падает, в `var/bot.log` остаётся предупреждение `llm_call не записан`.

Стоимость (только чтение журнала, ключи GigaChat не нужны):

```bash
docker exec homework-bot python -m hwcheck report cost var/events.jsonl
docker exec homework-bot python -m hwcheck report cost var/events.jsonl --since 2026-10-01
docker exec homework-bot python -m hwcheck report cost var/events.jsonl --env test
docker exec homework-bot python -m hwcheck report cost var/events.jsonl --json > cost.json
```

- `--env` — `prod` (по умолчанию), `test`, `dev` или `all`; тестовый трафик в отчёт по `prod` не входит.
- `--since` — с даты, день по московскому времени; `--json` — выгрузка вместо таблицы.
- `--pricing` — файл тарифов, по умолчанию `assets/pricing/gigachat.json` (цена за 1 млн токенов,
  источник и дата сверки — в самом файле). Цена `null` — в отчёте «тариф не задан», вызовы этой
  модели в суммы не входят. При смене тарифа правится файл, код не меняется.

Что считает отчёт:

- **по шагам и моделям** — вызовы, ошибки, токены и рубли;
- **стоимость одной проверки** — вызовы модели в трассах с `homework_uploaded`: среднее, медиана,
  максимум; загрузки, не дошедшие до модели, считаются отдельно и в среднее не входят;
- **разбор с тьютором** — вызовы в остальных трассах: на пользователя с разбором и на одну проверку;
- **на пользователя** — все вызовы пользователя, среди пользователей хотя бы с одной проверкой;
- **обращения по методике конкурса** — события с `component` на проверку и на пользователя в день,
  отдельно от `user_initiated`. Сводные события шагов (`vision_two_stage`, `solver`, `classifier`,
  `tutor`, `praise`) описывают те же вызовы модели, что и `llm_call`: в зачёт они не идут, иначе один вызов
  считался бы дважды (Положение, п. 5.4.1); общее число событий с `component` показано справочно.
  Ответ солвера из кэша (`from_cache: true`) — обращение без вызова модели, оно в зачёт идёт.

Записи до выкатки `llm_call` в стоимость не входят: отчёт пишет дату первого `llm_call` и число
проверок до неё. Бот на бесплатном лимите физлица фактически не платит — отчёт показывает цену тех
же токенов по платному тарифу.

## Семьи, прошедшие сценарий

Веха ментора конкурса: «семья прошла сценарий» — прислала домашку и дошла до верного ответа. Отчёт
считается по тому же журналу событий, сеть, база и ключи не нужны:

```bash
docker exec homework-bot python -m hwcheck report families var/events.jsonl
docker exec homework-bot python -m hwcheck report families var/events.jsonl --since 2026-10-01
docker exec homework-bot python -m hwcheck report families var/events.jsonl --json > families.json
```

`--env`, `--since` и `--json` — как у `report cost`. Аккаунты из `TEST_USERS` пишутся в журнал со
средой `test` и в отчёт по `prod` не входят.

| Строка отчёта | Что значит |
|---|---|
| Аккаунтов с любым действием | все, кто что-то сделал в боте за период: запустил, прошёл онбординг, прислал фото |
| Прислали домашку | семьи: аккаунты с событием `homework_uploaded` |
| Получили вердикт | бот разобрал и проверил хотя бы одно задание (`task_checked`) |
| Прошли сценарий | сумма двух строк ниже |
| — разобрал ошибку до верного ответа | разбор с тьютором дошёл до верного ответа (`error_fixed`) |
| — верное решение подтверждено | ошибок не разбирал, но бот подтвердил хотя бы одно верное задание — сразу или после ответа на уточняющий вопрос |
| Строгий счёт | вся домашка верна или разобраны все её ошибки; одно верное задание среди неразобранных ошибок сюда не входит |
| — из них разобрали все ошибки домашки | событие `homework_resolved` |
| Не прошли | по причинам: ошибки найдены, но разбор не доведён; бот не уверен; задания не разобраны |

- **Семья — это аккаунт, приславший домашку.** За ребёнка 1–4 класса фото присылает родитель,
  ребёнок 5–9 класса — сам. Двое детей со своими аккаунтами — две строки; аккаунт родителя
  старшеклассника в список не попадает, он домашку не присылает.
- В таблице — первые шесть знаков обезличенного идентификатора, полный — в выгрузке `--json`.
- Источник — метка первого запуска бота (`?start=s_<метка>`), в том числе до начала периода.
- Отчёт не знает, чьи это аккаунты: свои и связанные аккаунты из него убирает только `TEST_USERS`.
- **Какое число подавать.** «Прошли сценарий» — мягкий счёт, «строгий счёт» — жёсткий. Завысить
  отчёт хуже, чем занизить: пока ментор не подтвердил мягкое определение, в отчёты идёт строгий.
- С `--since` первая домашка и все счётчики считаются внутри периода: семья, пришедшая раньше,
  выглядит как новая. Источник при этом берётся из всей истории.
- «Разборов до верного» — число разборов, а не разных ошибок: повторный разбор той же ошибки
  по кнопке из старой сводки считается ещё раз. На «прошла / не прошла» это не влияет.
- Счётчики заданий — по первой проверке: ответ на уточняющий вопрос «не уверен» в «верно» в
  таблице не переносит, но в итог семьи входит.

## Шлюз моделей

Организаторы конкурса выдали команде ключ к шлюзу моделей с OpenAI-совместимым API. В `.env`:

```bash
LLM_GATEWAY_URL=https://shared1.multitool.works:4000/v1
LLM_GATEWAY_KEY=<ключ команды>          # в репозиторий и логи не попадает
SOLVER_MODEL=gw:gigachat-2-max          # префикс gw: — модель идёт через шлюз
TUTOR_MODEL=gw:gigachat-2-max
VISION_MODEL=gw:gemini-3.1-pro-preview  # чтение фото — с согласием по политике v2 и новее
VISION_MODEL_DOMESTIC=GigaChat-2-Max    # без префикса — GigaChat API напрямую
```

- Поставщика выбирает имя модели (`llm/router.py`). Бот не стартует, если модель назначена
  поставщику, который не настроен: в логе — имя настройки и чего не хватает.
- GigaChat через шлюз **изображения не принимает**, поэтому фото читает сторонняя модель шлюза
  (`VISION_MODEL`, выбор — `bench/reports/2026-09-28-gateway.md`). Это трансграничная передача:
  сторонней модели уходят только фото семей, чьё согласие дано по политике v2 и новее. Фото
  остальных — согласие по v0 или v1, бот без онбординга — читает `VISION_MODEL_DOMESTIC`.
- Семьи с согласием по прежней политике бот просит согласиться заново (не чаще раза в 3 дня,
  события `consent_renewal_asked`, `consent_renewed`); проверка при этом не останавливается.
- Промпт чтения фото следует за моделью: `VISION_PROMPT` — для `VISION_MODEL`,
  `VISION_PROMPT_DOMESTIC` — для `VISION_MODEL_DOMESTIC`; значение — версия файла
  `prompts/vision/<версия>.md`, по умолчанию `v3` (писался под GigaChat). Для сторонних моделей
  есть `v4-gemini` и `v4-claude`; **включать только после прогона стенда** — до него не
  проверено, что они не хуже `v3`. Версии без файла бот не принимает и не стартует.
- Какая модель и каким промптом прочитала фото, видно в журнале: `llm_call` с `kind: vision`,
  поля `model` и `prompt_version`.
- Лимита одновременных запросов у ключа нет; бот держит не больше `LLM_GATEWAY_CONCURRENCY` (8).
- Перегрузку шлюза (429, 5xx) и обрыв связи клиент повторяет с растущей паузой, ошибку запроса
  (4xx) — нет.
- Стоимость вызова шлюз сообщает в ответе: она пишется в `llm_call` (поле `cost`, рубли) и идёт в
  отчёт `report cost` вместо пересчёта по тарифу.

Проверить шлюз с сервера и остаток бюджета ключа (значение ключа не печатается):

```bash
docker exec homework-bot python -m hwcheck solve --no-cache "Вычисли: 17 * 23"
docker exec homework-bot python -c "
import httpx; from hwcheck.config import load_settings as s
c = s(); base = c.llm_gateway_url.removesuffix('/v1')
i = httpx.get(base + '/key/info', headers={'Authorization': 'Bearer ' + c.llm_gateway_key}).json()['info']
print('израсходовано', round(i['spend'], 2), 'из', i['max_budget'])"
```

Вернуться на GigaChat API: убрать префикс `gw:` у моделей (`VISION_MODEL=GigaChat-2-Max`,
`SOLVER_MODEL=GigaChat-2-Max`, `TUTOR_MODEL=GigaChat-2-Pro`) и пересоздать контейнер — `docker compose up -d --force-recreate bot`.

## Источники трафика

Антифрод конкурса просит сведения об источниках трафика (Положение, Прил. 2 п. 5). Для каждого канала,
поста или чата — своя ссылка на бота с меткой:

```
https://max.ru/<имя бота>?start=s_<метка>
```

Метка — латиница, цифры и дефис, до 32 знаков: `s_kanal-1`, `s_chat-3b`, `s_znakomye`. Слова
`invite`, `direct` и `unknown` меткой быть не могут: это служебные значения журнала. Имя бота —
из `GET /me` (строка `bot started` в `var/bot.log`). Ссылку без метки не раздаём: такой заход
попадёт в `direct` и от случайного не отличится.

В событие `bot_started` пишется поле `source`: метка из ссылки, `invite` (ссылка-приглашение
родителя или ребёнка), `direct` (заход без метки) или `unknown` (метка не разобрана; её текст в журнал
не пишется). Раздел «Источники трафика» отчёта `report cost` считает пользователей по источнику
первого запуска и сколько из них дошли до проверки. У пользователей, пришедших до выкатки меток,
источник — «не записан».

## Проверка базы знаний

Консольные команды для проверки ответов в базе знаний и загрузки словарей:

```bash
# Проверить непроверенные ответы по русскому языку (максимум 20 за раз)
docker compose exec bot python -m hwcheck kb review --subject russian

# Проверить ответы по английскому (другой предмет и лимит)
docker compose exec bot python -m hwcheck kb review --subject english --limit 10

# Загрузить словарь из файла
docker compose exec bot python -m hwcheck kb load-words --subject russian --source grade_list:2 /path/to/words.txt

# Загрузить карточки орфограмм (после миграции; идемпотентно — ON CONFLICT (code) DO UPDATE)
docker compose run --rm bot python -m hwcheck kb load-rules assets/kb/rules_russian.json
```

`DATABASE_URL` команды не требуют: она берётся из окружения контейнера бота (задана в
`docker-compose.yml`), поэтому пароль базы не попадает в историю команд.

Формат ввода при проверке:
- `y` — ответ верный, подтвердить
- `n` — ответ неправильный, отклонить
- `e` — исправить (вводится верный ответ, оригинальный отклоняется, исправленный сохраняется как проверенный)
- `q` — выйти из проверки

## Переключение dev → prod

В `.env` на VPS: `ENVIRONMENT=prod` и `TEST_USERS=<хэш>,<хэш>` — обезличенные id команды и
тестеров (поле `user` в `var/events.jsonl`), затем `docker compose up -d`. С этого момента события
идут в конкурсный зачёт (антифрод, Положение п. 2.2), а события тестеров пишутся с `env=test` и
в зачёт не попадают. Новый тестер — добавить его хэш в `TEST_USERS` и `docker compose up -d`.

## Ограничения текущей схемы

- Фото хранятся на диске VPS, а не в Object Storage; удаление по запросу пользователя — вручную
  по хэшу в имени файла (`rm var/photos/*/<хэш>-*`).
- Апдейты разных чатов обрабатываются параллельно, но в одном процессе и с очередями в его
  памяти: принятые и не обработанные апдейты теряются при падении процесса. Вызовы GigaChat API
  идут в один поток (PERS-тариф). При росте трафика — webhook + очередь в Redis (арх. §8).
