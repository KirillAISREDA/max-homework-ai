## 1. Продукт в двух абзацах

**«Домашка»** — ИИ-помощник в мессенджере MAX для школьников 1–9 классов. Ребёнок фотографирует тетрадь с
решённой домашкой (можно вместе со страницей учебника) — бот за минуту находит ошибки и **не выдаёт
готовый ответ**, а ведёт к нему подсказками (уровни 0→3, ответ — только на третьем). Родитель получает
итоги и не тратит вечер на проверку.

**Отличие:** арифметику проверяет не нейросеть, а детерминированный пересчёт (SymPy) — LLM не источник
истины; распознавание, объяснение и диалог — GigaChat. Для рукописного русского языка — посимвольный OCR
без «автоисправления» (LLM-vision скрывает 78–80 % орфографических ошибок, см. §6).

- Целевая аудитория: ученики 1–9 классов и их родители. 10–11 классы не берём (другие задачи).
- Сейчас проверяется: математика. Следующий предмет: русский язык (упражнения из учебника).
- Бот: «Домашка ИИ» в MAX. Команда: Кирилл (основатель — продукт, разработка, запуск) + ИИ-агенты
  (Claude Code): разработка по TDD, ревью агентами, PR на каждое изменение.

## 5. Архитектура и инварианты

Целевая архитектура — `docs/architecture.md` (Cloud.ru Evolution, GigaChat API, 1000+ DAU). Сейчас на
пилоте — один контейнер бота + Redis на VPS; переезд в Cloud.ru — когда потребует нагрузка или конкурс.

Инварианты (из `CLAUDE.md`, не нарушать): SymPy — источник истины по математике; FSM диалога управляет код;
ответ раскрывается только на уровне подсказки 3; LLM-шаги — контракт `(input) -> output` со схемой; промпты
версионированы; данные детей минимизированы (152-ФЗ): без ФИО и школы, id MAX не хранится в открытом виде.

Код (`src/hwcheck/`): `llm/` (клиент GigaChat, structured output) · `pipeline/` (normalize, vision, solver,
mathparse, validator, grade, classifier, tutor, generator) · `subjects/` (контракт модуля `base.py`, `kb_models.py`,
`math/module.py`, `registry.py`; PR #28) · `bot/` (max_api, models, handlers, check, pages, clarify, summary, crops, fsm,
runner; `onboarding/` — router, linking, student, parent, subject, context, state, texts, policy) · `db/` (pool, migrate,
migrations 001–003, repo, memory, kb, kb_memory, findings) · `events.py` · `photos.py` · `crypto.py` · `ocr_client.py` ·
`kb_cli.py` · `config.py` · `cli.py` (`hwcheck ping | vision | eval | solve | grade | tutor | generate | bot | keys |
report | bench | kb`). Отдельный сервис `ocrsvc/` (HTTP, движок по `OCR_ENGINE`, контейнер `homework-ocr` под профилем).

## 6. Качество: что знаем

- **Vision (математика):** GigaChat-2-Max в одном вызове с JSON отказывает на рукописи; свободная
  транскрипция читает. Печать учебника — почти идеально, рукописные цифры — с ошибками (850→860, «·»→«:»).
  Фото из мессенджера пережаты до 1280 px; апскейл бесполезен (модель сжимает вход сама), кропы не помогли.
- **Validator:** см. §2; не проверяет квадратные уравнения, неравенства, системы, умножение столбиком на
  многозначное, деление уголком. Два нерешённых уравнения подряд с ≥ 2 общими числами — ложная «ошибка».
- **Русский язык (исследование 13.09):** GigaChat vision сохраняет 3 % ошибок ученика, скрывает 78–80 %;
  ReadingPipeline (ai-forever, MIT, CPU/ONNX ~6 с) без языковой модели — сохраняет 66,5 %, скрывает 6 %, но
  искажает 17–24 % верных слов → только «кандидаты» с проверкой, не вердикт.
- **Английский язык (спайк 17.09, `docs/research/2026-09-17-en-handwriting-ocr.md`, датасет
  `school_notebooks_EN` — IELTS-уровень, не младшая школа, оговорка датасета):** GigaChat-2-Max
  и 3-Ultra на 20 листах (1000 слов, 14 подтверждённых ошибок) сохраняют дословно **0 %** ошибок
  (93 %/86 % точно исправлены до правильной формы), при этом читают обычный текст хорошо (80 %
  слов, CER 0,13); расхождение двух расшифровок как сигнал ошибки — полнота 7 %, точность 4 %
  (бесполезно, в отличие от математики 14.09). TrOCR-base-handwritten по кропам слов — хуже по
  общей точности (39 %, CER 0,45), но сохраняет 14 % ошибок (не ноль, но далеко от 66,5 %
  ReadingPipeline на русском) — предположительно из-за встроенного языкового декодера (LM),
  которого у ReadingPipeline нет. Путь (а) ReadingPipeline на латинице не измерен (ждёт
  контейнер Task 1). Стартовая сила вердикта для английского — только `candidate`.
- **Стенд моделей (14.09, `bench/reports/2026-09-14-models.md`):** главный источник ложных «ошибок» —
  распознавание рукописи (2-Max: 37 из 51 строки-вычисления с расхождением, CER 20 % на надёжных кейсах);
  3-Ultra/3-Pro не лучше; 3-Lightning не принимает фото и плохо размечает страницы; расхождение двух
  расшифровок — точный (89 %), но неполный (46 %) сигнал для уточняющих вопросов.
- **Уточняющие вопросы (14.09, шаг 1):** «не уверен» по неразборчивому знаку/строке или без итогового ответа →
  до 2 вопросов ученику (`bot/clarify.py`, фаза `clarifying`), ответ пересчитывает валидатор; ответ спрашиваем
  только при сошедшейся строке решения; результат — событие `task_clarified`. Шаг 2 (ошибки OCR) — по данным.
- **Журнал на проде (замер 28.09):** 301 запись с 04.09, `trace_id` — с 13.09 (52 трассы); все записи с 13.09 —
  `env=test` (4 тестера), в `env=prod` — 0 событий; на одну загрузку домашки ~6 вызовов компонентов по методике
  конкурса и ~9,4 тыс. токенов (распознавание ~5,1 тыс. токенов и 2,9 вызова на фото) — «десятки обращений»
  из формы конкурса были оценкой для полной домашки с диалогом тьютора, не замером.
- **Живые логи:** до исправлений 06–13.09 — 15 проверок, 0 «верно» (ложные ошибки парсера, склейка с чужим
  условием, падения). После PR #12–#15 проверено на альбоме с намеренными ошибками — вердикты верные; **на
  верной работе после выката ещё не проверено**.

## 6а. Рынок, конкуренты, регуляторика (исследование 14.09, источники — в презентации и ответах формы)

- **СберКот в приложении СберKids** (с 01.09.2026) — ближайший конкурент: математика 1–6 класс, фото страницы
  учебника или тетради, наводящие вопросы без готового ответа, подсказки на «правильно ли решил?»; отдельное
  приложение; про родителей и способ проверки арифметики — нет данных (1rnd.ru, 01.09.2026).
- **Готовые ответы:** ГДЗ (gdz.ru ~1,4 млн визитов/мес, SimilarWeb 08.2026), Skysmart «Решения», Алиса AI
  («Умная камера» — ответ с объяснением), Telegram-боты; ChatGPT в РФ без VPN недоступен, DeepSeek доступен.
- **Платформы** (Учи.ру, ЯКласс, Skysmart, Фоксфорд) — свои онлайн-задания или ручная проверка учителем;
  автоматической проверки фото рукописной домашки нет.
- **Рынок:** ~18 млн школьников (2024/25); 62 % школьников 8–15 лет пользуются нейросетями (Анкетолог, 09.2025);
  репетитор 500–2500 ₽/час, семьи тратят 5–6 тыс. ₽/нед (SuperJob, 04.2026).
- **MAX:** 107 млн регистраций (03.2026), > 85 млн в день (05.2026); «Сферум» (журнал, домашние задания) в MAX.
- **Риск 1 — рекомендации Минпросвещения (13.09.2026):** ученикам 1–4 классов самостоятельно пользоваться ИИ
  не рекомендуется; 5–9 — с разрешения учителя; на аттестации — нельзя. Это методические рекомендации, не закон,
  но для 1–4 классов нужен сценарий «под контролем родителя» (см. TODO).
- **Риск 2 — публикация ботов MAX:** по данным Habr (09.2025) публиковать ботов могут только верифицированные
  юрлица РФ, модерация до 48 ч. Проверить, как зарегистрирован «Домашка ИИ» и хватит ли этого для открытого
  привлечения пользователей.
- Стратегия цифровой трансформации образования (2022–2030): ИИ для автоматизации проверки домашних заданий
  (pnp.ru, 01.11.2023).

## 9. Уроки и грабли

- **GigaChat + жёсткий JSON + рукопись = отказ или галлюцинация.** Сначала свободный текст, структура —
  вторым вызовом текстовой модели.
- **PERS-фримиум = 1 поток.** Два параллельных прогона → 429; в боте семафор; eval не запускать параллельно
  с другими вызовами.
- **LLM «исправляет» ученика** — и орфографию (русский), и, вероятно, цифры. Всё, что проверяет ошибки
  ребёнка, должно опираться на детерминированную проверку или посимвольный OCR.
- **Ревью агентами окупается:** в PR #14 и #15 ревью заблокировало 3 сценария ложных «ошибок»/ложного
  «верно», которые тесты пропускали. Каждый PR с логикой проверки — через ревью с запуском злых входов.
- **Живые фото — лучший тест.** Сохранять фото (есть) и смотреть их при каждом спорном вердикте.
- **Прод с пользователями:** перед рестартом — события за 10 минут; код выкатывать `docker compose up -d
  --build bot`, Redis не трогать (13.09 рестарт Redis для проверки уронил загрузку тестера).
- **Логи контейнера пропадают при пересборке** — поэтому `var/bot.log`.
- **Распознавание нестабильно:** одно фото — разные расшифровки от прогона к прогону (живой альбом 14.09: мусорные
  равенства из уголка, выдуманные задачи и дроби). Правила проверки должны переживать мусор, а не только «чистую» запись.
- **`ruff format --check .` проверяет и код в markdown** — планы и документы с блоками python тоже форматировать.
- **`gh pr merge` может падать с GraphQL-ошибкой GitHub** — сливать через REST:
  `gh api -X PUT repos/KirillAISREDA/max-homework-ai/pulls/<N>/merge -f merge_method=merge`.
- **Локальный Docker не тянет образы** (прокси 127.0.0.1:10801) — тесты базы на кэшированном `postgres:16-alpine`
  (`hwcheck-test-pg`, порт 55432).
- **Один поллер на токен:** не запускать `hwcheck bot` локально, пока жив контейнер.
- **MAX `POST /answers` требует `message` или `notification`** — пустое тело `{}` даёт 400, кнопка «крутится»,
  апдейт падал целиком (онбординг у тестировщика 17.09). Документация об этом молчит; шлём `notification: ""`.
  Ошибка ack не должна ронять сценарий. Кнопки в проде без живого нажатия — не проверены.
- **`.env` на VPS с CRLF** — `grep|cut` по нему отдаёт хвост `
`, добавлять `tr -d '
'`; бот переживает.
- **Windows-окружение:** `TaskStop` фонового `uv run` не убивает дочерний python; heredoc с кавычками в bash
  ломается — правки через скрипты в scratchpad; Clash Verge (TUN, fake-ip) блокирует фреймы claude.ai в Chromium.
- **Хэш id `sha256("hwcheck:"+id)` обратим перебором** — в онбординге переходим на HMAC с секретом.
- **Цифры стенда проверять по кейсам до выводов:** первый прогон показал CER 67 % и «не найдено 50 %» — в основном
  артефакт разметки (номера с точкой, столбики, краткая запись); «0 ложных ошибок» у 3-Lightning — артефакт
  неверной роли страниц. Сравнивать модели на надёжных кейсах и по строкам-вычислениям.
- **Агенту-разметчику — писать файл сразу после каждого кейса:** первый запуск завис, разобрав ~40 фото и не
  записав ни одного файла.
- **Консоль Windows (cp1251)** роняет `print` со «→»; в CLI `stdout.reconfigure(errors="replace")`.
- **Ревью ловит дефекты плана, а не только кода:** в онбординге и каркасе 8 из 10 важных находок сидели в тексте плана
  (кнопка согласия без привязки к ссылке, `regrade` стирал находки, `.dockerignore` ломал сборку). Планы с полным кодом
  всё равно проходят ревью каждой задачи + финальное + безопасность.
- **Спайк раньше лимитов:** спецификация обещала OCR 1,5 ГБ, спайк показал 3 ГБ. Числа в инфраструктурные разделы —
  только после замера.
- **LLM-vision исправляет и латиницу:** GigaChat читает английскую рукопись точно (80 % слов), но исправляет 100 %
  ошибок ученика; расхождение двух расшифровок как сигнал бесполезно (полнота 7 %). Для языков — только посимвольный OCR.
- **На общем VPS без swap** OOM-killer может убить чужой контейнер; swap 4 ГБ включён 16.09, но памяти под OCR всё равно нет.
- **Субагент-исполнитель может «отложить» требование** (событие `kb_review`) — сверять отчёт со списком требований до ревью.
- **ReadingPipeline на CPU памяти нужно на порядок больше, чем «165 МБ весов»:** после загрузки моделей
  процесс уже занимает 609 МБ, после первого фото — 2,3–2,5 ГБ, пик на плотных (печатных) страницах —
  свыше 3 ГБ; `--memory=2g` штатно ловит OOM-kill. Планировать лимит контейнера `homework-ocr` от
  измеренного пика, а не от размера весов на диске — `docs/research/2026-09-17-readingpipeline-vps.md`.
- **Скачок памяти ReadingPipeline на первом фото — не веса и не torch, а `onnxruntime` при первом
  реальном вызове сессии:** ~620 МБ из скачка на OCR-шаге — артефакт `enable_cpu_mem_arena`/
  `enable_mem_pattern` (арена никогда не уменьшается, растёт под самый большой встреченный батч) и
  снимается без изменения текста; ~570 МБ на шаге сегментации — реальные активации сети на входе
  896×896, снимаются только уменьшением входа, а это роняет число распознанных слов на 10–31 % на
  реальных фото из MAX (мелкий рукописный текст на пониженном разрешении не сегментируется) — не
  делать. Апстримный код `OCR-model`/`SEGM-model` безусловно импортирует `torch`/`torchvision` на
  уровне модуля, даже когда реально используется только ONNX-путь без LM — голый импорт стоит
  ~200 МБ RSS зазря, убирается патчем без потери функциональности —
  `docs/research/2026-09-17-readingpipeline-memory.md`, `spikes/ocr_memory/patch_no_torch.py`.
- **`requirements.txt` репозиториев ai-forever (2022 год) не ставится как есть на Python 3.10**: нет
  колеса под `cp310` для `scikit-learn`/`scipy` старых версий, `openvino==2022.2.0` снят с PyPI,
  `onnxruntime==1.13.1` падает на новых ядрах (`cannot enable executable stack`). `ctcdecode` (нужен
  только для языковой модели, которую не используем) — не собирать, а подменять модулем-заглушкой:
  сборка kenlm+openfst тяжёлая и в спайке не нужна. Версии и обоснование — `spikes/ocr_ru/README.md`.
- **Пакет с именем `ocr` в `PYTHONPATH` затеняет апстримный `ocr` (`ReadingPipeline` ai-forever):**
  свой сервис назван `ocrsvc/`, а не `ocr/` — иначе `import ocr` в контейнере находит наш пакет вместо
  клонированного апстримного кода, и движок молча не грузится.
- **`spylls` (движок Hunspell) ставит свой top-level пакет `tests`:** в тестах проекта импортировать
  общие фикстуры как `from conftest import …`, не `from tests…` — иначе по совпадению имени пакета
  тесты видят чужой `tests` вместо своего.
- **`.dockerignore` исключает `assets` целиком:** каждый новый каталог данных под `assets/` — отдельная
  строка `!assets/<каталог>` (как `!assets/hunspell`, `!assets/kb`), иначе сборка образа бота тихо
  остаётся без файлов и падает не на сборке, а в рантайме.
- **Стенд в контейнере бота не видит `data/`:** compose монтирует только `var` и `.cache`; для `hwcheck bench ru` нужен `-v "$PWD/data:/app/data:ro"` (в runbook).
- **История ветки — тоже данные:** файл с персональными данными, закоммиченный и потом удалённый, остаётся в git; до пуша — `git filter-branch --index-filter 'git rm --cached …'` по диапазону `main..HEAD`, после — только переписывание общей истории.
- **Стенд на сторонних моделях — только на открытом датасете:** фото детей тестеров (`hw*`, `live*`) сторонним поставщикам не отправляются.
- **Повтор после таймаута ответа — второе списание:** запрос ушёл, модель могла отработать. Клиент шлюза повторяет только обрыв связи до отправки и ответы 429/5xx.
- **Стоимость от шлюза — недоверенный заголовок:** NaN ломает JSON журнала, ноль скрывает расход. В журнал идёт только конечное положительное число, иначе отчёт считает по тарифу.
- **Самые сильные модели не годятся для проверки «за минуту»:** GPT-5.5 и Gemini 2.5 Pro — 40–70 с на страницу и 12–17 ₽ за вызов; Gemini 3.1 Pro — 4 с и около рубля.
- **Фоновую задачу на Windows может завершить система при нехватке памяти** — долгие прогоны запускать по одной конфигурации; ответы моделей в кэше стенда, повтор бесплатный.
- **GigaChat ломает запись JSON, а не только содержание** (живая проба 28.09): теряет последнюю «}» и теряет «}, {» между объектами списка. Второе обычный разбор не замечает — ключи повторяются, побеждает последний, от списка остаётся один объект. Чинится в `llm/base.py::repair_json`; расклеиваются только объекты с одинаковым набором полей, иначе значение уходит чужому объекту.
- **Подставная модель в тестах не заменяет живую пробу:** три дефекта шага похвалы нашлись только на настоящих ответах GigaChat. Новый шаг с моделью — 10–15 живых вызовов до слияния, при нуле трафика на проде (ключ общий, один поток).
- **Обещание в тексте раньше функции — ложное обещание:** текст согласия обещал итог родителю, когда рассылки ещё не было (ревью PR #41). Обещание добавляется тем же PR, что и функция.
- **Сводное событие шага и `llm_call` — один вызов модели:** считать оба — завышать обращения конкурса (Положение, п. 5.4.1). Ответ солвера из кэша — исключение: вызова модели нет, событие шага — единственная запись об обращении.
- **`time.monotonic` на Windows идёт шагом ~16 мс:** мгновенный ответ мока даёт время 0.0, тест падает локально и блокирует pre-push. Время ответа — `perf_counter`, в тестах часы модуля подменяются.
- **`git add -A` в корне захватывает `.claude/worktrees/`** как вложенные репозитории — каталог в `.gitignore`.
- **Положение меняется — сверять с платформой конкурса:** копия в репозитории оказалась ранней редакцией (30 интервью, 70 пользователей, порог 25, конец этапа 15.10); действующая — 20, 50, 35 и 14.10, запрет своей и тестовой активности — Прил. 2 п. 5.1.3. Ментор был прав, расхождение было в нашей копии.
- **`.env` на VPS со смешанными концами строк:** разбор через `split('\r\n')` не находит строку с `\n`; править через `splitlines(keepends=True)` и проверять значение внутри контейнера после пересоздания.
- **Вложенные кавычки в `ssh "… python - <<EOF"` ломают скрипт молча** — скрипт файлом в scratchpad и `ssh host 'python3 -' < файл`.
- **Модель, собранная при старте, не знает о согласии семьи** (ревью PR #51): модули предметов держали модель чтения фото из настроек, и фото ушло бы сторонней модели без согласия. Безопасное значение — по умолчанию, небезопасное назначается проверке явно (`vision_override`), и каждый, кто шлёт фото, берёт модель из `vision_of`.
- **Параллельные чаты делят один цикл событий:** синхронная обработка фото (PIL) останавливала всех — тяжёлое в `asyncio.to_thread`. Очередь диспетчера ключуется чатом, состояние онбординга — пользователем: нужен свой замок.
- **Предел пропускной способности — одновременные обращения к моделям, а не сервер** (нагрузочный тест 29.09): процессор 2–6 %, а очередь растёт уже на 1 сообщении в секунду при 8 обработках.
- **Точность строки и итог проверки — разные вещи** (стенд 29.09): модель с лучшей транскрипцией дала меньше всего верных вердиктов. Главная причина «не уверен» — вторая модель не разобрала шаги решения; промпт чтения фото этого не лечит.
- **Кэш стенда не переживает смену промпта чтения:** транскрипция другая — разбор страницы считается заново, прогон стоит как новый.
- **Страница без заданий стоит вчетверо дороже:** лестница поворотов делает четыре чтения фото, если транскрипция не похожа на математику.
- **Остаток бюджета ключа шлюза** — `GET <корень шлюза>/key/info` (`spend`, `max_budget`); шлюз общий для команд и под нагрузкой изредка отвечает HTTP 500 — повтор проходит.
- **Две сессии в одном рабочем каталоге:** чужие незакоммиченные правки не трогать, свою работу вести в отдельном worktree; перенос — патчем `git diff` и `git apply --3way` на ветку от `main`.
- **Команду в документе, записанную скриптом, проверять глазами:** перенос строки в примере `docker run` записался буквальными символами вместо переноса (ревью PR #53).
- **Разметка сообщений MAX — только по запросу** (`fmt="markdown"`): в обычных ответах бота «*» — знак умножения, «_» — пропуск в слове, разметка превратила бы их в курсив. С разметкой уходит только экран согласия.
- **Сильная модель читает повёрнутую страницу, но не так же:** Gemini распознаёт математику при любом повороте, а текст отличается (сходство чисел 0,36–1,00). Поворот не лечит неудачный разбор — он даёт другую транскрипцию, а не лучшую.
- **Быстрая модель ≠ лучший вердикт:** промпт разбора писался под GigaChat; на 10 страницах одно задание — 8–12 пунктов, сравнивать модели меньше чем на 30 страницах бессмысленно.
- **Ребёнок тестового родителя — не тестер для журнала:** `TEST_USERS` знает только перечисленные хэши, новый аккаунт ребёнка пишется как `prod`. После каждого подключения с тестового аккаунта — добавлять хэш.
- **Смена версии политики просит согласие заново у всех** (`renewal.py`: любая версия, не равная текущей), причём текстом о смене модели чтения фото. Правка, не меняющая условий обработки (название), — на месте; новая версия — только вместе с новым текстом просьбы.
- **Настройка «по умолчанию выключено» и текст, который обещает функцию, расходятся молча:** текст, зависящий от функции, должен зависеть от той же настройки.
- **Подпись периода по датам при границе не в полночь** даёт общую дату у соседних периодов — родитель читает это как двойной счёт.
- **SQL, который негде выполнить локально, проверяется только в CI:** смотреть не на «зелёный», а на число пропущенных тестов — ноль пропущенных значит, что база была.
- **Bash-команда съедает обратную косую черту в скрипте из heredoc** — `\\n` превращается в перенос строки; скрипты правок писать файлом, не heredoc.
- **`gh pr merge` сразу после `pr create` сливает без CI** («no checks reported») — ждать `gh pr checks --watch` только когда чек уже появился, иначе проверять `gh run list --branch main`.
- **Пересчёт строки доказывает ошибку ребёнка, только если строка прочитана верно.** Распознавание теряет и путает цифры так, что строка остаётся «правдоподобной» (30.09: `9454 … = 8997` вместо `39454 … = 38997` сошлось само с собой). Если есть печатное условие пункта — сверять с ним; «верное значение» вида `3175254/61` — признак чтения, а не ошибки.
- **Вопрос и сверка ответа должны говорить об одном числе.** Модель, которая сама формулирует вопрос, спросит про промежуточное действие, а код ждёт итог — верный ответ ребёнка станет «пересчитай». Вопрос задаёт код; похвалу — тоже код.
- **Состояние чата в Redis — первый источник при разборе жалобы:** в нём строки, как их прочитал бот, находки и сессия тьютора с историей (ключ `fsm:<хэш>`, TTL сутки; только чтение, данные не печатать в отчёты).
