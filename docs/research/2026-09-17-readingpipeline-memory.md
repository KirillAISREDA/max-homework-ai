# Спайк памяти: можно ли снизить пик ReadingPipeline с ~3 ГБ до ≤ 1,5 ГБ на страницу

Дата: 2026-09-17 (follow-up к `docs/research/2026-09-17-readingpipeline-vps.md`). Вопрос: можно ли
снизить пиковую память OCR-контейнера (ReadingPipeline, ai-forever, без LM, CPU) с измеренных ~2,5–3 ГБ
до ≤ 1,5 ГБ на фото **без потери качества распознавания**, чтобы запустить русский этап на общем VPS
(доступно ~3,7–3,9 ГБ) без апгрейда до 16 ГБ / Cloud.ru. Код — `spikes/ocr_memory/` (throwaway, копия и
модификация `spikes/ocr_ru/`). Полный лог команд — в отчёте задачи
(`.superpowers/sdd/2026-09-16-subjects-framework/spike-memory-report.md`).

## Выводы (главное)

1. **Да, можно — 1454–1457 МБ пиковой RSS на 5 живых фото, текст побайтово идентичен
   неоптимизированному прогону.** Лучшая конфигурация — `spikes/ocr_memory/Dockerfile.notorch` (не
   ставит torch/torchvision вовсе) + `OCR_MEM_ORT_ARENA=0`, `OCR_MEM_ORT_MEMPATTERN=0` (выключены
   аллокатор-арена и mem-pattern у `onnxruntime.SessionOptions` для обеих ONNX-сессий), потоки и
   сегментация — без изменений (2 потока, вход сегментации 896×896, как у весов). Проверено не только
   `resource.getrusage().ru_maxrss` изнутри процесса, но и **реальным `docker run --memory=1536m`** —
   контейнер отработал все 5 фото без OOM-килла, `exit code 0`.
2. **Основная находка — где именно тратится память (инструментация по стадиям пайплайна, попытка #1).**
   На первом фото после загрузки моделей (609–615 МБ) память прыгает в два шага, оба — на первом
   реальном вызове `onnxruntime.InferenceSession.run()` соответствующей модели (ленивая инициализация
   сессии), не на этапах постобработки (contours/rotation/LineFinder — там RSS не меняется вовсе):
   - `SegmPrediction` (сегментация 896×896, LinkResNet): **+560–590 МБ** — это реальная память для
     активаций сети такого размера, она **не снижается** выключением arena/mem-pattern (снижается
     только уменьшением входа, но это ломает качество, см. п.4).
   - `OCRPrediction` (CRNN по кропам слов, батчи до 128): **+1080 МБ с настройками onnxruntime по
     умолчанию**, но только **+454–460 МБ** после выключения arena/mem-pattern — то есть ~620 МБ из
     исходного скачка было именно артефактом кэширующего аллокатора onnxruntime, не реальной
     потребностью модели.
   Дальнейший рост между фото (2,3 → 2,5 ГБ в исходном спайке) — тоже артефакт арены: она растёт под
   размер самого большого встреченного батча и никогда не уменьшается (`ru_maxrss` — это исторический
   максимум процесса, а не текущее потребление, поэтому «пик» после нескольких фото — не обязательно
   активная рабочая память, но именно он убивает контейнер по cgroup-лимиту).
3. **Две меры, которые снижают пик БЕЗ изменения текста (проверено побайтовым сравнением JSON
   `words` — text/box/confidence/line — на всех 5 фото):**
   - `enable_cpu_mem_arena=False` на обеих `onnxruntime.SessionOptions` — **2501 → 1621 МБ** (−35 %).
     Это делает почти всю работу; `enable_mem_pattern=False` в одиночку почти не помогает (2501 → 2262
     МБ), выключение обоих вместе — на 17 МБ лучше, чем только arena (1621 против 1638) — эффект
     mem-pattern маргинален по сравнению с arena.
   - **Убрать torch/torchvine из образа целиком** — **1621 → 1457 МБ** (ещё −10 %). Дано неочевидно: код
     апстрима (`OCR-model/ocr/predictor.py`, `SEGM-model/segm/predictor.py`, `tokenizer.py`,
     `transforms.py`) **безусловно импортирует `torch`/`torchvision` на уровне модуля**, даже когда
     реально используется только ONNX-путь (`OCRONNXCPUModel`/`SegmONNXCPUModel`) — торчовые классы
     (`OCRTorchModel`/`SegmTorchModel`) и `BeamSearcDecoder` (LM) в этом сценарии никогда не
     инстанцируются. Голый `import torch, torchvision` в этом образе стоит **~198 МБ RSS** (измерено
     отдельно: 135 МБ после numpy/cv2/onnxruntime/shapely/pyclipper/sklearn/albumentations → 334 МБ
     после `import torch, torchvision`), что математически объясняет разницу. Патч —
     `spikes/ocr_memory/patch_no_torch.py`: убирает `import torch`/`import torchvision` и замену
     `torchvision.transforms.Compose` на тривиальный Python-класс (`InferenceTransform` использует его
     только как последовательный вызов трансформаций — ни одной тензорной операции внутри при
     `return_numpy=True`, который используется всегда в ONNX-пути). Полное обоснование по каждой
     строке — комментарии в файле.
   - **Число потоков (`THREADS=1` вместо 2) памяти не снижает** (тот же пик 1621 МБ), но **вдвое
     увеличивает время** (p50 11,3 с / p95 23,8 с против 6,0/12,3 с) — не использовать.
4. **Уменьшение входа сегментации (896→640/768) — отклонено: экономит память, но ломает качество.**
   Гипотеза подтвердилась ровно наполовину:
   - ONNX-граф сегментации экспортирован апстримным `SEGM-model/scripts/torch2onnx.py` с
     `dynamic_axes` только по `batch_size` — высота/ширина **зашиты в граф** на момент экспорта
     (896×896). Патч одного лишь конфига препроцессинга (`resize` перед сессией) **не работает**:
     onnxruntime падает `INVALID_ARGUMENT: Got invalid dimensions ... Expected: 896` — граф
     действительно фиксирован по пространственным осям, это не гипотеза, а воспроизведённая ошибка.
   - Переэкспорт графа из `.ckpt` под нужный размер (`spikes/ocr_memory/export_segm_onnx.py`,
     тот же код, что и апстримный `torch2onnx.py`, только с параметризуемым размером) **технически
     работает** и даёт нужную память: 640×640 → **1420 МБ**, 768×768 → **1490 МБ** (оба под целевые
     1,5 ГБ).
   - **Но текст меняется сильно, не в пределах допуска ≤ 2 %:** число распознанных слов падает на
     **10–31 %** на всех 5 фото (например, `notebook-answer57.jpg`: 32 → 22 слова при 640, → 26 при
     768). Мелкий рукописный текст на реальных фото из MAX (клетка, блики, наклон) на пониженном
     разрешении сегментации теряется — это не шум сравнения (посимвольные различия видны даже в
     распознанных цифрах: `"1000"` пропадает, `"906"`↔`"200"` и т.п.). **Понижать разрешение
     сегментации для этого домена (тетради, а не чистый печатный текст) нельзя** — отклонено по
     критерию качества из брифа, несмотря на то что по памяти это самый эффективный рычаг.
5. **OpenVino (попытка #5) не понадобился** — цель ≤ 1,5 ГБ с неизменным текстом достигнута попытками
   1+2+4 (инструментация → arena/mem-pattern off → без torch), решено не тратить дополнительный прогон
   на общем VPS сверх необходимого (см. правило спайка «стоп при достижении цели»).
6. **Побочный эффект — небольшое замедление.** Отключение arena/mem-pattern убирает переиспользование
   буферов onnxruntime между вызовами: p50 вырос с 5,2 до 6,2–6,4 с, p95 — с 12,1 до 12,5–13,4 с (на тех
   же 5 фото, тот же `--cpus=2`). Это приемлемая цена за помещение в 1,5 ГБ; таймаут клиента (см.
   предыдущий спайк, p95×2 = 60 с по худшему случаю с печатными страницами) пересматривать не нужно —
   рукописный p95 всё ещё далеко внутри бюджета.

## Рекомендация по инфраструктуре

**Пересматривает вывод предыдущего спайка.** Было: «не размещать на этом VPS без изменений, нужен
Cloud.ru с резервированием ≥ 3 ГБ». Стало: **на этом VPS размещать можно** с лимитом контейнера

рукопись за пределами 5 протестированных фото; то, что печатные страницы учебника **не должны**
попадать в этот контейнер по архитектуре, но если классификатор ошибётся — печатные страницы дают
самый большой скачок памяти в исходном спайке, до 3 ГБ; и на общий факт, что доступно на VPS сейчас
~3,7–3,9 ГБ и он общий с ботом+Redis+PostgreSQL+чужими контейнерами). Образ — `Dockerfile.notorch` +
`OCR_MEM_ORT_ARENA=0 OCR_MEM_ORT_MEMPATTERN=0` (см. рецепт ниже). **16 ГБ / Cloud.ru для этого этапа
больше не требуются** — это меняет вывод из `docs/PROJECT_MEMORY.md` §4 от 17.09.

## Рецепт лучшей конфигурации

`spikes/ocr_memory/Dockerfile.notorch` (полный Dockerfile) — коротко:
- Тот же образ, что `spikes/ocr_ru`/`spikes/ocr_memory/Dockerfile`, **без строк `pip install torch
  torchvision`**.
- Перед `pip install --no-deps ./OCR-model ./SEGM-model` — `python patch_no_torch.py`: убирает
  безусловные `import torch`/`import torchvision` из `ocr/predictor.py`, `ocr/transforms.py`,
  `ocr/tokenizer.py`, `segm/predictor.py`, `segm/transforms.py` и заменяет
  `torchvision.transforms.Compose` на локальный класс без зависимостей (см. подробное обоснование по
  каждой строке — докстринг файла).
- `ENV OCR_MEM_ORT_ARENA=0 OCR_MEM_ORT_MEMPATTERN=0 OCR_MEM_THREADS=2 MALLOC_ARENA_MAX=2
  OMP_NUM_THREADS=2` — дефолты уже зашиты в образ.
- `run.py` монки-патчит `onnxruntime.SessionOptions` **до** создания `PipelinePredictor` (перехватывает
  вызов `ort.SessionOptions()` внутри апстримного `OCR-model`/`SEGM-model` кода через общий
  `sys.modules['onnxruntime']`, без правки апстримных файлов) — выставляет `enable_cpu_mem_arena` и
  `enable_mem_pattern` из окружения.
- Сегментация и OCR — родное разрешение весов (896×896 / 64×512), не тронуто.

## Гипотеза из брифа — подтверждена наполовину

Бриф предполагал, что скачок на первом фото (~1,6 ГБ) — это «аллокатор torch CPU / арены
intra-op-потоков, не веса». По факту: **не torch** (torch вообще не участвует в вычислениях на
ONNX-пути — только висит мёртвым импортом) — это **onnxruntime**: часть скачка (OCR, ~620 МБ) —
действительно аллокатор-артефакт (arena/mem-pattern, снимается настройками сессии без потери
качества), а часть (сегментация, ~570 МБ) — **не артефакт, а реальные активации сети** на входе
896×896 (не снимается без потери качества, см. п.4). Разбить эти два источника и было главной ценностью
инструментации по стадиям (попытка #1).

## Риски и что не проверено

- **Только 5 фото / 3 уникальные страницы тетради** (та же выборка, что в предыдущем спайке, — для
  сравнимости) — как и там, это не статистика, а иллюстрация порядка величины. Более плотный или мелкий
  почерк другого ребёнка может дать другой пик — рекомендованный лимит 1,75–2 ГБ учитывает это частично,
  но не проверен на такой выборке.
- **Печатные страницы (учебник) не тестировались в этом спайке заново** — в предыдущем они давали пик
  до 3,06 ГБ и не должны попадать в этот контейнер по архитектуре (печатное условие идёт через
  GigaChat-vision). Если классификатор «тетрадь/учебник» ошибётся и печатная страница попадёт сюда —
  лимит 1,75–2 ГБ, вероятно, недостаточен; это тот же риск, что был отмечен в предыдущем спайке, он не
  снят этим спайком.
- **`MALLOC_ARENA_MAX=2` и `OMP_NUM_THREADS=2` не изолированы как отдельные рычаги** — стояли
  одинаково («на всякий случай», стандартная гигиена для контейнеров с ограниченной памятью) во ВСЕХ
  попытках этого спайка, включая baseline (попытка 1 тоже уже с `MALLOC_ARENA_MAX=2`, поэтому и
  baseline 2501 МБ уже ниже, чем 3063 МБ из самого первого спайка на 7 фото — часть разницы, вероятно,
  отсюда, а не только из-за иного набора из 5 фото вместо 7). Отдельно не измерялось, сколько именно
  дают эти две переменные без остальных изменений — если понадобится урезать ещё сильнее, стоит
  проверить в первую очередь.
- **Конкурентные запросы (несколько фото параллельно в одном или разных контейнерах) не проверялись** —
  тот же непроверенный риск, что и в предыдущем спайке; данный спайк снижает пик на *один* прогон, не
  меняет ничего в конкурентном сценарии.
- **Патч `patch_no_torch.py` — точечный под эту версию апстрима** (закреплённый коммит через
  `git clone --depth 1`, но upstream не запинен по хэшу) — если ai-forever изменит структуру
  `predictor.py`/`transforms.py`, `assert`-проверки в патче упадут явной ошибкой на этапе сборки (не
  тихо сломают пайплайн) — это осознанный компромисс throwaway-кода, а не прод-практика.
- **Время выросло на ~15–20 % по p50** (5,2 → 6,2–6,4 с) из-за выключения arena/mem-pattern — приемлемо
  для текущего таймаута клиента (60 с из предыдущего спайка), но стоит держать в уме при дальнейшей
  оптимизации задержки.
