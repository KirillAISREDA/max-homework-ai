# Спайк: ReadingPipeline (ai-forever) в контейнере на CPU VPS

Дата: 2026-09-16/17 (сессия — задача 1 каркаса предметов). Цель — измерить на реальном железе (общий
VPS, CPU, `--memory=2g --cpus=2`, как в проде) время, память и качество ReadingPipeline без LM на
живых фото из MAX, и решить: лимит памяти контейнера, таймаут клиента, «VPS или Cloud.ru». Код —
`spikes/ocr_ru/` (throwaway). Полный лог команд — в отчёте задачи (`task-1-report.md`).

## Выводы

1. **Образ собирается без Docker-хоста Кирилла** (локальный Docker не тянет образы, см. грабли
   PROJECT_MEMORY) **и без изменения логики** черновика из задачи, но версии зависимостей и
   структура сборки — другие: сборка на VPS 16.09 с первой попытки после разведки, детали и
   обоснование каждого отличия — `spikes/ocr_ru/README.md`. Главное: `requirements.txt` репозиториев
   2022 года частично не ставится на Python 3.10 (нет колеса, версия снята с PyPI, инцидент со старым
   `onnxruntime` на этом ядре) — версии подняты до ближайших совместимых; `ctcdecode` (тяжёлая C++-сборка
   для LM, которую мы не используем) заменён модулем-заглушкой вместо сборки.
2. **Класс слов в весах — `shrinked_text`**, не `"text"` (пример из README репозитория) и не
   `"handwritten_text_shrinked_mask1"` (предположение в черновике задачи). `confidence` в
   `pred["predictions"]` не реализован в апстриме (без LM `BestPathDecoder` отдаёт только текст) —
   поле в JSON всегда `null`, пока пайплайн не доработан отдельно.
3. **Время на CPU (`--cpus=2`, как в проде на общем VPS):** на 5 фото рукописной тетради — p50 5,7 с,
   p95 11,7 с; если считать по всем 7 фото выборки (2 из них — печатные страницы учебника с 180–205
   словами, которые в проде через этот контейнер не идут, см. п.6) — p50 5,8 с, p95 30,0 с. Рекомендация
   по таймауту клиента — из худшего наблюдённого случая (см. п.7).
4. **Память — главная находка спайка, и она проблема.** После загрузки моделей процесс уже занимает
   609 МБ; после первого же обработанного фото (даже лёгкого) память подскакивает до ~2,3–2,5 ГБ и
   дальше растёт с плотностью страницы: пик на всех 7 фото — 3063 МБ. Под `--memory=2g` контейнер
   штатно убивается OOM-killer'ом на самом плотном фото (печатная страница учебника, 205 слов;
   `dmesg`: `anon-rss:2070900kB`, то есть уже у cgroup-лимита). Под `--memory=3g` все 7 фото
   обрабатываются без ошибок. **Лимит 1,5 ГБ из `constraints.md` для контейнера `homework-ocr`
   недостижим с этим пайплайном как есть** — см. «Решения».
5. **Точность (ручная сверка, 5 фото, есть заранее человеком выверенные эталоны в `bench/golden/`):**
   38,7 % строк-ответов распознаны дословно, 54,8 % — с шумом в операторах/лишними символами, но
   восстановимы человеком, 6,5 % потеряны. **Ошибки ребёнка почти всегда сохраняются** (в отличие от
   GigaChat-vision, 13.09-исследование, где скрывалось 78–80 %) — но не всегда: на 1 из 6 неверных
   ответов (написано «900», верно было бы «906») в 2 из 3 переснятых фото той же строки распознавание
   выдало именно «906» — совпадение с математически правильным ответом. Редко (2 из 18 инстансов
   неверных строк, 11 %, на одном-единственном примере), но именно такой риск и был причиной отказа от
   LLM-vision — держать в уме при интеграции (эталон из учебника + «проверь слово», не голый вердикт OCR).
6. **Печатный текст учебника через этот пайплайн не гонять.** Он не источник таких проблем сам по
   себе (обработался, слова похожи на правду), но именно печатные страницы дали оба всплеска памяти
   (2,5→3,0 ГБ и 3,0→3,06 ГБ) и оба самых долгих прогона (19,8 с и 30,0 с) — в архитектуре печатное
   условие и так идёт через GigaChat-vision по фото учебника, а не через этот OCR.
7. **Решение по инфраструктуре: не на этом VPS, пока не снижена память.** Свободно на VPS сейчас
   ~3,7–3,8 ГБ (общий хост, там же бот+Redis+PostgreSQL); контейнеру ReadingPipeline реально нужно
   ~2,5–3 ГБ пиковой памяти (без запаса на всплеск при печатной странице в кадре или на конкурентные
   запросы). Колокация без обособленного лимита памяти и без дальнейшей оптимизации — риск уронить
   либо OCR, либо прод при первом же плотном фото. Рекомендация — Cloud.ru с отдельным
   резервированием памяти (≥ 3 ГБ) на этот контейнер, а на VPS возвращаться только после снижения
   пиковой памяти (см. «Риски / не проверено»).
8. **Формат слов из брифа достаточен для Task 9, но с оговоркой:** `box` = `bbox` — координаты в
   системе исходного (неповёрнутого) фото; для кропа слова после `RestoreImageAngle` нужен
   `rotated_bbox` вместе с повёрнутым изображением. Для многоколоночных страниц (наш реальный случай —
   левая/правая колонка примеров №52 на одной физической строке) `line_idx` один и тот же для обеих
   колонок — в пайплайне уже есть `column_idx`, но бриф его не запрашивал; для последующей сборки в
   строки (Task 9) он, вероятно, понадобится.

## Формат вывода на фото — подтверждено по факту

```json
{
  "seconds": 5.8,
  "words": [
    {"text": "651", "box": [335, 520, 415, 553], "confidence": null, "line": 3}
  ]
}
```

- `text` — распознанный текст слова (`shrinked_text`), посимвольно, без LM.
- `box` = `bbox` из `pred["predictions"]` — координаты в исходном (неповёрнутом) фото.
- `confidence` — всегда `null`: `OcrPredictor` без LM использует `BestPathDecoder`, который отдаёт
  только строку; чтобы получить уверенность, нужно менять декодер в `OCR-model/ocr/tokenizer.py`.
- `line` = `line_idx` от `LineFinder` — индекс строки на странице. Для двухколоночных страниц (как
  №52 в тесте: слева `651+126…`, справа `306-138…` на той же высоте) колонки получают **один и тот же**
  `line_idx` — их различает `column_idx`, который есть в `pred["predictions"]`, но не запрошен в
  формате брифа. Для Task 9, если нужна сборка «слово → строка задания» на многоколоночных страницах,
  стоит добавить `column_idx` в контракт.

### Задание №52 (3 фото одного листа: три попытки сфотографировать одну и ту же тетрадь)

Ребёнок специально ошибся в 6 из 8 примеров (эталон/вердикт — из `bench/golden`); задача теста — не
проверить арифметику, а проверить, **сохраняет ли OCR то, что реально написано**, включая ошибки.

| # | Написано (эталон) | Фото 1 `…aa8` | Фото 2 `…34f` | Фото 3 `…eba` |
|---|---|---|---|---|
| 1 | 651+126=**850** (неверно, верно 777) | дословно (шум в знаке «+») | дословно (шум в знаке) | дословно (лишняя цифра-шум) |
| 2 | 379−253=**1000** (неверно, верно 126) | искажено → «1600» | искажено → «1600» | **дословно** — «1000» |
| 3 | 306−138=**162** (неверно, верно 168) | искажено (потерян минуенд «306») | искажено (потерян минуенд «306») | дословно (306 восстановим через «О6») |
| 4 | 402−243=**159** (верно) | дословно (306→«4о2», цифра/буква) | дословно | искажено — ответ «159» не распознан вовсе |
| 5 | 453×2=**900** (неверно, верно 906) | искажено → **«906»** (= правильный ответ!) | искажено → «200» | искажено → **«906»** (= правильный ответ!) |
| 6 | 321×3=**963** (верно) | дословно (с шумовым префиксом) | дословно (с шумовым префиксом) | дословно (с шумовым префиксом) |
| 7 | 5×171=**905** (неверно, верно 855) | дословно (со сдвоенной цифрой-шумом) | **дословно**, чисто | дословно (со сдвоенной цифрой-шумом) |
| 8 | 6×98=**612** (неверно, верно 588; сама запись двусмысленная — «612» или «672») | дословно | дословно | дословно |

Итог по 24 строкам-инстансам (8 строк × 3 фото): **дословно 10 (42 %), искажено, но восстановимо
человеком 13 (54 %), потеряно 1 (4 %)**. Из 18 инстансов «неверных» строк (6 строк × 3 фото) —
2 инстанса (оба строка 5, «900»→«906») совпали с математически **правильным** ответом; это
единственный найденный случай такого рода на весь тест, и он воспроизводится только на этой одной
строке (не на всех неверных ответах). Строка 3 (потерян минуенд «306») и строка 5 — самые слабые
места; в остальном цифры, которые ребёнок реально написал, включая шум/лишние символы, доходят до
JSON, а не заменяются на «правильные».

Три фото — три разных прогона сегментации+OCR по трём разным фотографиям одного листа (не три
запуска модели на одном и том же фото): расхождения между колонками таблицы — это чувствительность к
углу/свету/резкости съёмки, а не недетерминированность модели. В отличие от GigaChat-vision
(13.09-исследование: разные расшифровки одного и того же фото от прогона к прогону), тут при
одинаковом входе выход один и тот же — но реальные повторные фото всё равно отличаются по качеству
распознавания.

### Задание №57 (словарная задача, 2 фото: решение + следующая страница с ответом)

| Строка (эталон) | Распознано | Вердикт |
|---|---|---|
| «Бабушка − 20 л.» | «Б» + «Бабушка» + «а» + «20л.» | дословно (слово разбито на технические токены, но без ошибок в буквах/цифрах) |
| «Внучка − в 4 раза м., ? л.» | «Внучка» + «в» + «раза» + «м.,» | искажено — цифра «4» и «?» не опознаны уверенно как отдельные токены |
| «Осталось − 10 л.» | «О» + «стало» + «сь» + …(рядом «-го») | искажено — слово «Осталось» побуквенно верно, число «10» не найдено |
| «Было − ? л.» | не найдено отдельной строкой | потеряно |
| «1) 20 : 4 = 5 (л.) − внучка.» | «1)20:4=5(л.)-» + «внучка» | **дословно**, почти без шума |
| «2) 20 + 5 + 10 = 35 (л.) − было.» | «2)2075+10-» + «=3» + «5(л.)» + «было» | искажено (шум в «+5»→«75»), но финальный ответ «35» и слово «было» — верны |
| «Ответ: было − 35 луковиц.» (на 2-м фото) | «Ответ:» + «было» + «-35» + «луковец» | искажено — одна буква («луковиц»→«луковец»), остальное дословно |

Итог: 2 из 7 строк дословно, 4 искажены, но восстановимы, 1 потеряна — в целом та же картина, что и
на №52. Особо: этот альбом (`live0914-55-57`) раньше на GigaChat-vision давал нестабильные и
«галлюцинирующие» расшифровки от прогона к прогону (см. заметку в `bench/golden/…long-division.json`)
— на ReadingPipeline такой нестабильности по конструкции быть не может (один вход — один выход), хотя
качество на конкретно этой сложной странице (деление уголком, обрезанная соседняя страница в кадре)
всё равно среднее: цифры длинного деления читаются фрагментами, не равенствами, — сборка равенств
«748 : 2 = 374» из обрывков уголка — отдельная, нерешённая в этом спайке задача постобработки
(вероятно, для контракта нужен другой источник истины по делению столбиком, не посимвольный OCR).

### Печатные страницы учебника (2 фото, без детальной сверки)

Обработались без ошибок (182 и 205 слов, оба класса `shrinked_text`), но детальной построчной сверки
не делал — эти два фото не входят в целевой сценарий для этого контейнера (печатное условие задания в
проде идёт через GigaChat-vision по фото учебника, не через ReadingPipeline). Важны здесь не как
кейс качества, а как источник обоих всплесков памяти и обоих самых долгих прогонов — см. «Выводы» п.6.

## Решения

- **Лимит памяти контейнера `homework-ocr`:** текущий `1,5 ГБ` из `constraints.md` недостижим —
  пайплайн уже после загрузки моделей и одного фото стабильно работает в районе 2,3–2,5 ГБ. Рекомендация:
  поднять лимит минимум до **3 ГБ** (запас над измеренным пиком 3063 МБ на смешанной выборке) **и**
  завести отдельную задачу на снижение памяти (см. риски) прежде чем фиксировать лимит окончательно.
- **Таймаут клиента:** p95 × 2 по худшему наблюдённому случаю (все 7 фото, включая печатные страницы,
  которые всё же могут попасть в кадр) = 30,0 × 2 = **60 с**. Если удастся гарантировать на входе
  только рукописные фото тетради — можно снижать до ~25 с (p95 рукописных 11,7 × 2), но это требует
  доверия к классификатору «тетрадь/учебник» до OCR, отдельно не проверялось.
- **VPS или Cloud.ru:** **не размещать на этом VPS без изменений.** Свободно ~3,7–3,8 ГБ, при этом сам
  бот+Redis+PostgreSQL уже используют остальное; контейнеру с пиком ~2,5–3 ГБ там не остаётся запаса
  даже на один параллельный плотный запрос, не говоря об одновременной работе с ботом. Рекомендация —
  Cloud.ru с выделенным резервированием памяти под этот контейнер (≥ 3 ГБ), либо дальнейшая работа над
  снижением памяти пайплайна и повторный тест на VPS после этого.

## Грабли сборки (кратко; подробности с обоснованием каждой замены — `spikes/ocr_ru/README.md`)

- `pip install -r ReadingPipeline/requirements.txt` тянет `ctcdecode` (git+parlance/ctcdecode,
  тяжёлая C++-сборка kenlm+openfst) только ради LM, которую сознательно не используем — заменено
  клонированием репозиториев по отдельности + модуль-заглушка вместо реальной сборки.
- `--index-url https://download.pytorch.org/whl/cpu` вместо `--extra-index-url` ломает установку
  torch — pip перестаёт видеть на PyPI чистые python-пакеты вроде `flit_core`.
- `numpy` должен быть `<2` (закреплён `1.23.1`) — иначе torch/opencv/onnxruntime падают на
  ABI-несовместимости с NumPy 2.x.
- `onnxruntime==1.13.1` на этом VPS (Ubuntu 22.04.5, ядро 5.15) падает при импорте (`cannot enable
  executable stack`) — версия поднята до `1.17.3`.
- `scikit-learn==1.0.1`, `scipy==1.4.1`, `openvino==2022.2.0` — нет колеса под Python 3.10 / версия
  снята с PyPI — подняты до `1.3.2` / `1.10.1` / `2024.6.0` соответственно.
- `pyclipper==1.3.0` собирается из исходников (нужен `g++`) — единственная реальная компиляция в образе.
- `pipeline_config.json` из весов рассчитан на GPU (`device: cuda`, `runtime: Pytorch`, пути на
  `.ckpt`, LM включён) — `run.py` патчит его в рантайме на CPU/ONNX/без LM; пути в конфиге
  относительные — нужен `os.chdir` в директорию весов до создания `PipelinePredictor`.

## Риски и что не проверено

- **Снижение памяти не исследовалось предметно** — не проверены: меньший `batch_size` в
  `OCRPrediction` (сейчас 128 из конфига весов, не менялся), `num_threads=1` вместо 2, рантайм
  `OpenVino` вместо `ONNX` (может иметь другой профиль памяти), явный `gc.collect()`/переинициализация
  сессий между фото, обработка фото по частям вместо целой страницы разом.
- Скачок памяти с 609 МБ до ~2,3–2,5 ГБ происходит уже на первом, произвольном фото — не локализовано,
  какая часть (сегментация 896×896, ONNX Runtime arena, потоки intra/inter_op) отвечает за основной
