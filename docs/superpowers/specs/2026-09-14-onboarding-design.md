# Онбординг, согласие родителя и профиль ученика — дизайн

Дата: 2026-09-14. Статус: согласован с Кириллом по разделам, ждёт вычитки спецификации.
Подпроект 1 из двух (подпроект 2 — проверка упражнений по русскому языку, отдельная спецификация).

## 1. Контекст и цель

Бот «Домашка» работает в prod на VPS (1–9 класс, проверка математики). Сейчас любой пользователь сразу
присылает фото: нет ролей, класса, предмета и, главное, **согласия родителя на обработку данных ребёнка**
(152-ФЗ; п. 5.6 Положения Sber500xDisrupt возлагает законность обработки на нас). Без этого нельзя
привлекать 70 реальных пользователей к 15.10.

Цель подпроекта — первый вход, связка «родитель ↔ ребёнок», согласие, профиль (класс, предмет) с
переходом в следующий класс, лист ожидания по предметам и уведомления родителю.

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Кто ставит бота | Оба сценария: ставит родитель (A) или ребёнок сам и пересылает ссылку родителю (B) |
| Что спрашиваем у ребёнка | Только класс и предмет, кнопками; имя не спрашиваем |
| Доступ до согласия | Проверка закрыта до согласия родителя; пока ждём — пример проверки на готовом фото |
| Аккаунты | Всегда два аккаунта MAX (ребёнок и родитель), связка ссылкой в любую сторону |
| Предметы | Все предметы класса на экране; недоступные — «скоро» + лист ожидания |
| Аудитория | Только 1–9 классы |
| Уведомления родителю | Режим на выбор, переключается: «сразу» / «сводка в выбранное время» / «не присылать»; по умолчанию сводка в 20:00 МСК |
| Хранилище | PostgreSQL |
| Политика обработки данных | В чате: выжимка при согласии + кнопка «Полный текст»; текст версионируется в репозитории |
| Размещение данных | VPS 193.247.73.243 — Москва (HOSTKEY, по геолокации IP; подтвердить договором) |

## 3. Объём

**Входит:** выбор роли; класс; предмет; связка аккаунтов ссылкой и запасным кодом; согласие с версией
политики; пример проверки; меню и команды; переход в следующий класс; лист ожидания; режимы уведомлений
и сводка; отзыв согласия и удаление данных; усиление хэша id (HMAC); воронка событий.

**Не входит:** еженедельные отчёты с рекомендациями (неделя 5), проверка предметов кроме математики,
mini-app, подписи детей по имени, несколько родителей у одного ребёнка.

## 4. Сценарии

Шаг онбординга **не хранится отдельно, а выводится из данных** в PostgreSQL: нет роли → роль; ученик без
класса → класс; без предмета → предмет; без подтвердившего родителя → «нужно разрешение». Redis (TTL 24 ч)
хранит только временное — открытое родителем приглашение, ожидающее ответа.

### 4.1. Ребёнок пришёл сам (`bot_started` без метки)

1. «Привет! Я Домашка — проверяю домашку и помогаю разобраться с ошибками. Кто ты?» —
   [Я ученик] [Я родитель].
2. «В каком ты классе?» — кнопки 1–9 (3×3).
3. «Какой предмет сейчас?» — кнопки предметов класса (§5): доступные — как есть, недоступные — «🔜 История».
   Недоступный: «Проверку по истории пока учу — сообщу, когда появится. А пока могу проверить математику»,
   запись в лист ожидания, повтор выбора предмета.
4. «Чтобы начать, нужно разрешение родителя. Перешли маме или папе сообщение ниже 👇» — отдельным
   сообщением ссылка `https://max.ru/<username>?start=p_<токен>` и запасной код «4F7K-92QD» («если ссылка не
   открылась — отправь боту код»); кнопка [Посмотреть пример проверки].
5. После согласия родителя ребёнку: «Родитель разрешил! 🎉» + инструкция: что прислать (фото страницы
   тетради целиком, можно вместе с фото учебника, до 4 фото), сколько ждать (около минуты), что дальше
   (сводка, разбор ошибок подсказками — готовых ответов бот не даёт).

До согласия фото **не скачивается**: «Сначала нужно разрешение родителя» + [Отправить ссылку ещё раз]
+ [Пример проверки].

**Пример проверки** — текстом, без картинки (отправка изображений требует загрузки через API MAX, которой
в клиенте пока нет): как выглядит присланная страница («№17: 803 + 169 = 753»), сводка бота («№17 — есть
ошибка (строка 1) ❌» с кнопкой-муляжом) и первая подсказка тьютора. Данных ребёнка в примере нет.

### 4.2. Родитель пришёл по ссылке ребёнка (`?start=p_<токен>`)

1. «Ваш ребёнок (4 класс) хочет пользоваться Домашкой» + выжимка о данных (§10.3) + [Полный текст] +
   [Согласен] [Отказать].
2. [Согласен] → согласие, связка, приглашение погашено (одна транзакция); ребёнку — сообщение из 4.1 п.5.
3. «Как присылать вам итоги?» — [Сразу после проверки] [Сводка в 20:00] [Другое время] [Не присылать].
   Сводка/другое время → время (18:00 / 19:00 / 20:00 / 21:00) → часовой пояс (§9.3).
4. [Отказать] → приглашение погашается (повторно открыть нельзя); ребёнку: «Родитель пока не разрешил»
   (без подробностей) + [Отправить ссылку ещё раз]; событие `consent_declined`. Родитель в `users` не
   сохраняется, если у него нет других детей.

### 4.3. Родитель пришёл сам (`bot_started` без метки → [Я родитель])

1. Выжимка о данных + [Полный текст] + [Согласен].
2. Режим уведомлений (как 4.2 п.3).
3. «Отправьте ребёнку ссылку — он откроет бота в своём MAX» — ссылка `?start=c_<токен>` + запасной код.
   Приглашение хранит `consent_given_at` и `policy_version`.
4. Ребёнок открыл ссылку → класс → предмет → сразу инструкция (согласие уже есть; запись `consents`
   создаётся в момент привязки с `given_at` из приглашения). Родителю: «Ребёнок (4 класс) подключился».
5. [Пригласить ещё ребёнка] — в меню родителя, новое приглашение `c_`.

### 4.4. Правила связки

- Приглашения одноразовые, живут 7 дней. Просрочено/использовано → «Ссылка устарела — попроси новую»;
  у создавшей стороны в меню [Отправить новую ссылку].
- У ребёнка один подтвердивший родитель; у родителя — сколько угодно детей. Второй родитель → вежливый
  отказ («у ребёнка уже подключён родитель»); смена — через отзыв согласия.
- Связать аккаунт сам с собой — отказ.
- Роль и ссылка не совпали: родительский аккаунт открыл `c_` → «эту ссылку нужно открыть в аккаунте
  ребёнка»; аккаунт ученика открыл `p_` → «эту ссылку нужно открыть в аккаунте родителя». Новый
  пользователь по `p_` становится родителем, по `c_` — учеником (выбор роли пропускается).
- Запасной код: текст вида `XXXX-XXXX` (дефис необязателен) у пользователя без завершённого онбординга
  или из меню — погашает приглашение как ссылка. Не больше 5 попыток ввода в час на пользователя.
- Неизвестная/битая метка в `bot_started` → обычный старт.
- **Не проверено живьём:** приходит ли `bot_started` с меткой, если у пользователя бот уже запущен. Если
  нет — основным путём для таких пользователей становится запасной код (текст сообщения это уже учитывает).

### 4.5. Меню и команды

Команды (`PATCH /me/commands` при старте бота): `/menu`, `/help`. Повторный `bot_started` без метки у
завершившего онбординг — меню.

- Ученик: [Сменить предмет] [Сменить класс] [Как прислать домашку] [Удалить мои данные].
- Родитель: [Уведомления] [Пригласить ребёнка] [Отправить новую ссылку] [Отозвать согласие и удалить данные].

Родитель прислал фото → «Фото домашки присылает ребёнок в своём аккаунте Домашки».
Ученик с недоступным текущим предметом прислал фото → «По истории пока не проверяю. Переключиться на
математику?» [Да, математика] [Выбрать другой].

### 4.6. Переход в следующий класс

Хранится класс и учебный год, в котором он указан; текущий класс — вычисляется (фоновой задачи нет):

```
school_year(d) = d.year, если d.month >= 9, иначе d.year - 1      # 2026/27 → 2026
current_grade  = grade + (school_year(today) - grade_year)
```

- Первое взаимодействие ученика в новом учебном году (`school_year(today) > grade_asked_year`) —
  «Новый учебный год! Ты теперь в 5 классе?» [Да] [Остался в 4 классе] [Другой класс]. Ответ →
  `grade = ответ`, `grade_year = grade_asked_year = school_year(today)`. Пока не ответил — работает
  вычисленный класс.
- `current_grade > 9` → «Домашка — для 1–9 классов. Спасибо, что занимался с нами!» + [Удалить мои данные];
  проверка закрыта. Родителю — уведомление.
- Смена класса меняет список предметов; текущий предмет вне класса → выбор предмета заново.

## 6. Данные (PostgreSQL)

Сырой id MAX нигде не лежит в открытом виде: для поиска — HMAC-хэш (§10.1), для отправки сообщений —
зашифрованная копия.

```sql
CREATE TABLE users (
  id               bigserial PRIMARY KEY,
  max_user_hash    text NOT NULL UNIQUE,          -- тот же хэш, что поле user в events.jsonl
  max_user_id_enc  bytea NOT NULL,                -- Fernet(USER_ID_KEY)
  role             text NOT NULL CHECK (role IN ('student', 'parent')),
  created_at       timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE student_profiles (
  user_id          bigint PRIMARY KEY REFERENCES users ON DELETE CASCADE,
  grade            smallint CHECK (grade BETWEEN 1 AND 9),
  grade_year       smallint,                      -- учебный год, в котором указан grade (2026 = 2026/27)
  grade_asked_year smallint,                      -- в этом учебном году уже спросили про класс
  subject          text,
  parent_user_id   bigint REFERENCES users ON DELETE SET NULL,
  CHECK (parent_user_id IS DISTINCT FROM user_id)
);

CREATE TABLE parent_settings (
  user_id          bigint PRIMARY KEY REFERENCES users ON DELETE CASCADE,
  notify_mode      text NOT NULL DEFAULT 'digest' CHECK (notify_mode IN ('instant', 'digest', 'off')),
  digest_time      time NOT NULL DEFAULT '20:00',
  utc_offset_min   smallint NOT NULL DEFAULT 180,
  last_digest_at   timestamptz
);

CREATE TABLE consents (                             -- юридическая запись, без FK: переживает удаление
  id               bigserial PRIMARY KEY,
  parent_hash      text NOT NULL,
  student_hash     text NOT NULL,
  policy_version   text NOT NULL,
  given_at         timestamptz NOT NULL,
  revoked_at       timestamptz
);
CREATE UNIQUE INDEX consents_one_active_parent ON consents (student_hash) WHERE revoked_at IS NULL;

CREATE TABLE invites (
  token_hash       text PRIMARY KEY,                -- sha256 токена из ссылки
  short_code       text NOT NULL UNIQUE,
  kind             text NOT NULL CHECK (kind IN ('student_invites_parent', 'parent_invites_student')),
  created_by       bigint NOT NULL REFERENCES users ON DELETE CASCADE,
  consent_given_at timestamptz,                     -- для parent_invites_student
  policy_version   text,
  expires_at       timestamptz NOT NULL,
  used_at          timestamptz,
  used_by          bigint REFERENCES users ON DELETE SET NULL
);

CREATE TABLE homeworks (
  id               bigserial PRIMARY KEY,
  student_user_id  bigint NOT NULL REFERENCES users ON DELETE CASCADE,
  subject          text NOT NULL,
  tasks_total      smallint NOT NULL,
  tasks_correct    smallint NOT NULL,
  tasks_wrong      smallint NOT NULL,
  tasks_uncertain  smallint NOT NULL,
  errors_resolved  smallint NOT NULL DEFAULT 0,
  created_at       timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX homeworks_student_time ON homeworks (student_user_id, created_at);

CREATE TABLE subject_waitlist (
  user_hash        text NOT NULL,
  subject          text NOT NULL,
  grade            smallint NOT NULL,
  created_at       timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_hash, subject)
);

CREATE TABLE login_attempts (                       -- лимит ввода запасного кода
  user_hash        text NOT NULL,
  attempted_at     timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX login_attempts_user_time ON login_attempts (user_hash, attempted_at);
```

- `homeworks` — упрощённая `homeworks` из архитектуры §6.1 (без разбивки по заданиям): основа уведомлений и
  сводки. `id` проверки кладётся в `ChatState` (Redis), чтобы закрытый разбор увеличил `errors_resolved`.
- События остаются в `var/events.jsonl` (перенос в БД — вне объёма).
- Согласие на пару «родитель—ребёнок» только на хэшах: при удалении данных профили удаляются, у согласия
  ставится `revoked_at`, запись остаётся доказательством законной обработки (**вычитать юристу**).

**Встраивание в `bot/handlers.py`** (файл уже ~470 строк — логика онбординга в него не добавляется;
`_dispatch` маршрутизирует):

1. `bot_started` с меткой `p_`/`c_` → онбординг (приглашение).
2. Пользователь не найден / онбординг не завершён / `/menu`, `/help` / кнопки `ob:`, `menu:` / текст-код → онбординг.
3. Ученик без согласия прислал фото → блокировка (§4.1), фото не скачивается.
4. Ученик: новый учебный год → вопрос о классе (§4.6) перед проверкой.
5. Ученик с согласием и доступным предметом → текущий сценарий проверки без изменений; после сводки —
   `homeworks` + уведомление «сразу».
6. Родитель прислал фото → «фото присылает ребёнок».

`ONBOARDING_REQUIRED=false` — аварийный выключатель: маршрутизация пропускает шаги 1–4 (текущее
поведение). В prod с реальными пользователями — только на время исправления поломки.

**Инфраструктура:** контейнер `homework-postgres` (`postgres:17-alpine`, том `postgres-data`, без портов,
healthcheck `pg_isready`, лимит 256 МБ); бот `depends_on: service_healthy`. Ежедневный `pg_dump` в
`var/backups`, хранение 7 дней. Новые зависимости `asyncpg`, `cryptography` → `docs/components.md`.

## 8. Переход на HMAC-хэш (зачем — §10.1)

- `anonymize(user_id) = HMAC-SHA256(ID_HASH_KEY, str(user_id)).hexdigest()[:16]`.
- `EventLog` сверяет `TEST_USERS` и с новым, и с legacy-хэшем, пока тестеры не обновлены.
- Ключи Redis (`fsm:<хэш>`) и имена фото (`<хэш>-…`) переходят на новый хэш: открытые разборы тестеров
  сбрасываются один раз.

## 9. Уведомления родителю

### 9.1. «Сразу»

После сводки проверки у ребёнка: «Ребёнок (4 класс) проверил домашку по математике: 4 задания — 3 верно,
1 с ошибкой (№19), разбирает с подсказками». При нескольких детях одного класса — «ребёнок 1 / 2» в
порядке привязки. Закрытие разбора отдельного сообщения не порождает (попадает в сводку).

### 9.2. Сводка

Фоновая задача в процессе бота, тик 60 с:

```
local_now  = utc_now + utc_offset_min
slot_local = дата(local_now) + digest_time
отправить, если slot_local <= local_now < slot_local + 3 ч
            и (last_digest_at IS NULL или last_digest_at < slot_utc)
окно данных: homeworks.created_at в (last_digest_at, utc_now]
после отправки: last_digest_at = slot_utc
```

Содержимое — по каждому ребёнку: домашек, заданий, верно / ошибок / не уверен, ошибок разобрано. **Пустой
день — без сообщения.** Бот лежал в слот → отправка после подъёма, но не позже 3 ч после слота.

### 9.3. Настройка

Время: 18:00 / 19:00 / 20:00 / 21:00. Пояс (кнопки): Калининград МСК−1, Москва МСК, Самара МСК+1,
Екатеринбург МСК+2, Омск МСК+3, Красноярск МСК+4, Иркутск МСК+5, Якутск МСК+6, Владивосток МСК+7,
Магадан МСК+8, Камчатка МСК+9.

### 9.4. Сбои

Отправка не удалась (родитель заблокировал бота) → событие `notify_failed`, повторов нет. Каждая
отправка — событие с `component="notifier"`.

## 10. Приватность и безопасность

### 10.1. Идентификаторы

- Текущий `sha256("hwcheck:" + id)` обратим перебором диапазона id MAX → переход на HMAC с секретом.
- Сырой id — только Fernet-шифротекст в `users.max_user_id_enc`. Ключи `USER_ID_KEY`, `ID_HASH_KEY` —
  в `.env` на VPS **и копия вне VPS** (без `USER_ID_KEY` бот не сможет писать пользователям, без
  `ID_HASH_KEY` — найти их).
- В логах и событиях — только хэши; транскрипции — только при `ENVIRONMENT=dev` (как сейчас).

### 10.2. До согласия

Хранятся только роль, класс, предмет, хэш и шифротекст id. Фото не скачиваются, в `var/photos` не
попадают, в GigaChat не уходят.

### 10.3. Выжимка согласия (черновик, текст — в `bot/texts.py`)

Что обрабатываем: класс, выбранный предмет, фото домашних заданий (хранятся 30 дней), результаты проверок,
идентификатор MAX (в зашифрованном виде). Зачем: проверка домашки, разбор ошибок, уведомления родителю.
**Кому передаём: фото и текст заданий — в GigaChat API (ПАО Сбербанк) для распознавания и проверки.**
Где: серверы в России. Как отозвать: меню → «Отозвать согласие и удалить данные». Полный текст —
кнопка [Полный текст] (политика версии `POLICY_VERSION`, сообщениями в чат).

### 10.4. Отзыв согласия и удаление данных

Из меню родителя (для выбранного ребёнка) или ученика, с подтверждением «Удалить безвозвратно?»:

1. Одна транзакция: удалить `users` ребёнка (каскадом `student_profiles`, `homeworks`), его записи
   `subject_waitlist`, `login_attempts`, непогашенные приглашения; `consents.revoked_at = now()`.
2. После коммита: фото `var/photos/*/<хэш>-*`, ключи Redis `fsm:<хэш>`.
3. Второй стороне — уведомление («согласие отозвано, данные удалены»).
4. Родитель без детей и сам удаляет данные → удалить его `users` (каскадом `parent_settings`).
5. `var/events.jsonl` (обезличенные записи) сохраняется для аудита конкурса — это указано в политике.

## 11. Ошибки и крайние случаи

- PostgreSQL недоступен при старте — бот не поднимается (health контейнера); во время работы — общий
  перехват `handle_update`: «попробуй ещё раз» + `update_failed`.
- Согласие + связка + погашение приглашения — одна транзакция; повторное [Согласен] или повторное
  открытие ссылки ничего не дублирует (погашенное приглашение, частичный уникальный индекс согласий).
- Сообщение ребёнку «родитель разрешил» не дошло — `notify_failed`; при следующем сообщении ребёнок сразу
  видит открытый доступ (шаг выводится из данных).
- Гонка двух родителей на одного ребёнка — побеждает первая транзакция (уникальный индекс), второму — отказ.
- Отсутствуют `USER_ID_KEY`/`ID_HASH_KEY`/`DATABASE_URL` при `ONBOARDING_REQUIRED=true` — бот не стартует
  с понятной ошибкой.

## 12. Аналитика (события `events.jsonl`)

Все — с `trace_id`, обезличенным `user`, `user_initiated=true` для действий пользователя:

`onboarding_role_chosen{role}`, `onboarding_grade_chosen{grade}`, `onboarding_subject_chosen{subject,
available}`, `subject_waitlist{subject, grade}`, `invite_created{kind}`, `invite_opened{kind, via:
link|code, result: ok|expired|used|invalid|role_mismatch|has_parent|self}`, `consent_given{policy_version}`,
`consent_declined`, `child_linked`, `notify_mode_set{mode}`, `grade_confirmed{changed}`, `graduated`,
`photo_blocked_no_consent`, `data_deleted{initiator}`, `notify_sent{kind}`, `notify_failed{kind, error}`.

Воронка: роль → класс → предмет → ссылка создана → ссылка открыта → согласие → первая проверка.
