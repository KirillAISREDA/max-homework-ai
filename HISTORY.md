**Принятые решения:**

**Следующие шаги:** прогнать `hwcheck ping` с реальными кредами; собрать первые фото и запустить `hwcheck eval` — замерить латентность vision.

## 2026-08-31 — Сессия 3: первый датасет, нормализация фото, главный риск подтвердился

**Сделано:**
- `hwcheck ping` — ОК (перс-аккаунт PERS, латентность 0.66 с). B2B-ключ упёрся в 402 (нет пакета токенов).
- Кирилл собрал датасет: 31 реальное фото тетрадей (пережаты мессенджером: 1280×960, ~130 КБ, EXIF вырезан).
- Ветка `feat/image-normalization`: нормализация (EXIF-поворот, ресайз, JPEG, композитинг прозрачности на белый) + retry-лестница ориентаций 0→270→90→180 в `recognize_page`. Code review: 2 HIGH исправлены (MIME/имя файла после перекодирования; альфа-канал в чёрный фон).

**Результаты офлайн-оценки (3 прогона по 31 фото):**
| Прогон | Найдены задания | Латентность медиана/p90 |
|---|---|---|
| v1 без поворотов | 4/31 | 1.3 / 4.5 с |
| v1 + повороты | **8/31** | 4.8 / 6.4 с |
| v2 («отказ запрещён») + повороты | 4/31 | 5.0 / 7.3 с |

**Главные выводы:**
1. **Латентность — НЕ риск**: 5–7 с на фото со всеми попытками, при цели 20–60 с на проверку запас большой.
2. **Риск — способность GigaChat читать рукопись**: 23/31 фото — отказ «неразборчивый почерк» (2-Max и 3-Ultra отвечают одинаково); там, где распознал — ошибки чтения (№4.30 → «432», перепутаны знаки) при confidence 0.9 → confidence не откалиброван.
3. GigaChat сжимает вход до фиксированного внутреннего разрешения (tokens_in=9294 и для 1280px, и для 2048px) — апскейл бесполезен, **кропы дадут реальный выигрыш разрешения**.
4. В API уже есть `GigaChat-3-Ultra` (не только линейка 2) — на нашу задачу пока не лучше.

**Решения/гипотезы на следующую сессию:**
- Двухэтапный vision: сегментация зон заданий → кроп каждой зоны → распознавание по-кропово (кроп получает весь внутренний бюджет разрешения GigaChat). Это соответствует арх. §3.3.
- Проверить фото без пережатия мессенджером (оригинал с телефона, 3–4k px) — вдруг дело в качестве сжатия.
- Держать в уме ветку арх. §11.2: специализированный OCR за интерфейсом `VisionClient`, если accuracy не дотянет.

**Дополнение (та же сессия, после скриншота ЛК):** токенов достаточно (фримиум до 30.08.2027: Ultra ~50M, Max ~24.4M, Pro 40M, Lite 250M; потрачено 630k Max). Проведены решающие эксперименты:
1. **Кропы НЕ помогли**: половинки фото (двойной эффективный масштаб) → тот же отказ во всех ориентациях на всех 3 тестовых фото.
2. **Свободная расшифровка без JSON вскрыла галлюцинации**: на фото с дробями 5-го класса Max «прочитал» формулы метода Ньютона, Ultra — выдуманные последовательности. Отказы в JSON-режиме — это честность модели; при принуждении она сочиняет.

**Вывод: GigaChat vision (2-Max и 3-Ultra) не читает детскую рукопись на пережатых мессенджером фото (1280px). Это ограничение модели, а не промпта/разрешения/формата.**

**Развилка (решение за Кириллом после проверки оригиналов фото):**
- Путь А: оригиналы без пережатия (3–4k px) читаются приемлемо → в проде требуем качественное фото + получаем максимум от MAX Bot API.
- Путь Б (арх. §11.2): специализированный рукописный OCR за `VisionClient`. Ориентир: у SberAI есть открытый датасет школьных тетрадей `school_notebooks_RU` и обученные на нём OCR-модели — кандидат на self-hosted в Cloud.ru. GigaChat остаётся для reasoning-шагов (Solver, Tutor, Classifier).
- Параллельно (не блокируется vision): неделя 2 — Solver + Validator (SymPy), вход у них текстовый.

## 2026-08-31 — Сессия 4: Solver + Validator + Grade (ядро недели 2)

**Сделано (ветка `feat/solver-validator`):**
- `mathparse`: безопасный парсер школьной нотации — смешанные числа «8 3/7», запятая в десятичных, деление «:», цепочки «a=b=c», маркеры пунктов «а)»/«№4», √ и ^. Точная арифметика (Rational, rationalize при парсинге — без float-погрешностей). Вход недоверенный: whitelist символов, лимиты на длину чисел/степени/вложенные степени перед sympy (он парсит через eval).
- `validator`: детерминированный пересчёт каждого шага (ok/mismatch/skipped) + сравнение ответов (True/False/None).
- `solver`: эталонное решение через GigaChat (structured output) + обязательная самопроверка эталона Validator'ом (`ref_ok`); невалидный эталон не кэшируется и уходит в эскалацию. Файловый кэш по sha256(model+prompt_version+task) — прообраз Redis-кэша из арх. §4.
- `grade`: вердикт correct/wrong/uncertain, первый ошибочный шаг, описки (slip) при верном ответе.
- CLI: `hwcheck solve "текст"`, `hwcheck grade --task ... --step ... --answer ...`.
- TDD: тесты писались первыми; итого 73 теста в проекте.

**Живой smoke (GigaChat-2-Max):** задача на скорость решена верно (1.2 с, 312 токенов); ошибка ученика «7 1/8 + 2 5/8 = 9 5/8» найдена детерминированно (валидатор: посчитано 39/4, написано 77/8) — ядро «LLM решает, SymPy проверяет» работает.

**Отложено осознанно:** function calling `calc()` в Solver (арх. §4) — добавим, если у эталонов появятся арифметические ошибки на реальных заданиях; Comparator/Classifier — неделя 3.

## 2026-08-31 — Сессия 6: Classifier + Tutor FSM + Generator (неделя 3)

**Сделано (ветка `feat/classifier-tutor-generator`):**
- `classifier`: таксономия ошибок (calc_error/strategy_error/condition_misread/slip/incomplete/unclear) поверх фактов Validator'а; confidence < 0.6 → принудительно `unclear` (fail-safe арх. §3.3).
- `tutor`: FSM уровней подсказок 0→3. Инварианты в коде и под тестами: уровень повышает код (+1 за реплику без верного ответа, потолок 3), **эталон попадает в промпт только на уровне 3**, `resolved` ставится детерминированной сверкой `compare_answers` (распознан и эквивалентный ответ: «9 6/8» = «9 3/4»).
- `generator`: похожая задача, эталон проверяется SymPy; 1 retry, затем отброс (None).
- CLI: `hwcheck tutor` — интерактивная демка полного цикла (solve → grade → classify → диалог), `hwcheck generate`.
- 87 тестов, всё зелёное.

**Живой smoke:** диалог тьютора на «7 1/8 + 2 5/8 = 9 5/8»: классификатор — calc_error/сложение смешанных чисел (0.9), уровень 1 — намёк, уровень 2 — приём, «9 6/8» распознан как верный ответ, тьютор сам предложил сократить дробь. Генератор выдал задачу с валидным эталоном.

**Итого по плану**: недели 2–3 из архитектуры (§10) закрыты по функциональности CLI-пайплайна. Дальше — неделя 4: MAX Gateway + Core API, либо закрытие развилки по vision (ждём оригиналы фото).

## 2026-09-01 — Сессия 7: двухэтапный vision — развилка закрыта в пользу GigaChat

Кирилл прислал новую домашку (4 фото из Telegram: учебник + тетрадь). Одноэтапный vision снова отказал даже на чётком почерке. Решающий эксперимент: **свободная транскрипция без JSON читает те же страницы** — печатный учебник почти идеально, рукопись прилично. Отказы порождала связка «vision + жёсткий JSON + сегментация в один вызов».

**Новый vision-пайплайн (ветка `feat/vision-two-stage`):**
1. Vision-транскрипция свободным текстом (`prompts/vision/v3.md`), лестница ориентаций с дешёвым гейтом `looks_like_math` (мусор не тратит второй вызов).
2. Структурирование транскрипции текстовой моделью в `VisionPage` (`prompts/vision_structure/v1.md`, через надёжный `chat_structured`).

**Результаты:**
| Датасет | Одноэтапный (лучший) | Двухэтапный |
|---|---|---|
| Старый, 31 фото | 8/31 | **28/31** |
| Новая домашка, 4 фото | 0/4 | **4/4** |

~3k токенов на фото (втрое дешевле лестницы), 8–13 с. Полный цикл на реальном задании №8 («книга 180 страниц»): фото → транскрипция → структура → Solver → Validator → **correct** ✓.

**Остаточные проблемы (в работе):**
- Точность цифр рукописи (999→99, 50→30): лечится сверкой с печатным условием учебника — сценарий «фото учебника + фото тетради» (печать читается ~идеально). В backlog.
- 3 провала из 31: геометрия с углами (структуризация не признала за задания — править промпт), бледное фото, таймаут.
- Урок: PERS-фримиум = 1 параллельный запрос; два одновременных прогона → 429. В проде — семафор (арх. §8), в CLI не запускать eval параллельно.

## 2026-09-01 — Сессия 8: бот MAX (неделя 4, локальный polling)

**Сделано (ветка `feat/max-bot`):** формат API сверен с dev.max.ru (base `platform-api2.max.ru`, токен в Authorization, GET /updates + marker, POST /messages c inline_keyboard, POST /answers).
- `bot/max_api.py` — клиент; `bot/models.py` — толерантные модели апдейтов (незнакомые поля не роняют бота).
- `bot/fsm.py` — FSM диалога (idle/checking/review/tutoring) за протоколом `StateStore`; in-memory сейчас, Redis при деплое.
- `bot/handlers.py` — сценарий: фото → двухэтапный vision → по заданиям (есть условие → Solver+grade; голый столбик → только Validator) → сводка с кнопками «Разобрать №N» → классификатор + диалог тьютора. `_pseudo_ref` для примеров без условия: «эталон» = значение, посчитанное валидатором.
- `events.py` — журнал вызовов компонентов под конкурсную метрику и антифрод: sha256-обезличенный user, dev/prod разделение.
- Семафор GigaChat (1 поток фримиума) во всех вызовах — больше никаких 429.
- CLI `hwcheck bot` — long polling, публичный URL не нужен. 109 тестов.

**Ждём MAX_TOKEN** (Кирилл регистрирует бота) → живой end-to-end в мессенджере.
