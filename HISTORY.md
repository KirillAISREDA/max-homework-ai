**Сделано:**

**Результаты офлайн-оценки (3 прогона по 31 фото):**
| Прогон | Найдены задания | Латентность медиана/p90 |
|---|---|---|
| v1 без поворотов | 4/31 | 1.3 / 4.5 с |
| v1 + повороты | **8/31** | 4.8 / 6.4 с |
| v2 («отказ запрещён») + повороты | 4/31 | 5.0 / 7.3 с |

**Главные выводы:**
1. **Латентность — НЕ риск**: 5–7 с на фото со всеми попытками, при цели 20–60 с на проверку запас большой.
2. **Риск — способность GigaChat читать рукопись**: 23/31 фото — отказ «неразборчивый почерк» (2-Max и 3-Ultra отвечают одинаково); там, где распознал — ошибки чтения (№4.30 → «432», перепутаны знаки) при confidence 0.9 → confidence не откалиброван.
3. GigaChat сжимает вход до фиксированного внутреннего разрешения (tokens_in=9294 и для 1280px, и для 2048px) — апскейл бесполезен, **кропы дадут реальный выигрыш разрешения**.
4. В API уже есть `GigaChat-3-Ultra` (не только линейка 2) — на нашу задачу пока не лучше.

**Решения/гипотезы на следующую сессию:**
- Двухэтапный vision: сегментация зон заданий → кроп каждой зоны → распознавание по-кропово (кроп получает весь внутренний бюджет разрешения GigaChat). Это соответствует арх. §3.3.
- Проверить фото без пережатия мессенджером (оригинал с телефона, 3–4k px) — вдруг дело в качестве сжатия.
- Держать в уме ветку арх. §11.2: специализированный OCR за интерфейсом `VisionClient`, если accuracy не дотянет.

**Дополнение (та же сессия, после скриншота ЛК):** токенов достаточно (фримиум до 30.08.2027: Ultra ~50M, Max ~24.4M, Pro 40M, Lite 250M; потрачено 630k Max). Проведены решающие эксперименты:
1. **Кропы НЕ помогли**: половинки фото (двойной эффективный масштаб) → тот же отказ во всех ориентациях на всех 3 тестовых фото.
2. **Свободная расшифровка без JSON вскрыла галлюцинации**: на фото с дробями 5-го класса Max «прочитал» формулы метода Ньютона, Ultra — выдуманные последовательности. Отказы в JSON-режиме — это честность модели; при принуждении она сочиняет.

**Вывод: GigaChat vision (2-Max и 3-Ultra) не читает детскую рукопись на пережатых мессенджером фото (1280px). Это ограничение модели, а не промпта/разрешения/формата.**

**Развилка (решение за Кириллом после проверки оригиналов фото):**
- Путь А: оригиналы без пережатия (3–4k px) читаются приемлемо → в проде требуем качественное фото + получаем максимум от MAX Bot API.
- Путь Б (арх. §11.2): специализированный рукописный OCR за `VisionClient`. Ориентир: у SberAI есть открытый датасет школьных тетрадей `school_notebooks_RU` и обученные на нём OCR-модели — кандидат на self-hosted в Cloud.ru. GigaChat остаётся для reasoning-шагов (Solver, Tutor, Classifier).
- Параллельно (не блокируется vision): неделя 2 — Solver + Validator (SymPy), вход у них текстовый.

## 2026-08-31 — Сессия 4: Solver + Validator + Grade (ядро недели 2)

**Сделано (ветка `feat/solver-validator`):**
- `mathparse`: безопасный парсер школьной нотации — смешанные числа «8 3/7», запятая в десятичных, деление «:», цепочки «a=b=c», маркеры пунктов «а)»/«№4», √ и ^. Точная арифметика (Rational, rationalize при парсинге — без float-погрешностей). Вход недоверенный: whitelist символов, лимиты на длину чисел/степени/вложенные степени перед sympy (он парсит через eval).
- `validator`: детерминированный пересчёт каждого шага (ok/mismatch/skipped) + сравнение ответов (True/False/None).
- `solver`: эталонное решение через GigaChat (structured output) + обязательная самопроверка эталона Validator'ом (`ref_ok`); невалидный эталон не кэшируется и уходит в эскалацию. Файловый кэш по sha256(model+prompt_version+task) — прообраз Redis-кэша из арх. §4.
- `grade`: вердикт correct/wrong/uncertain, первый ошибочный шаг, описки (slip) при верном ответе.
- CLI: `hwcheck solve "текст"`, `hwcheck grade --task ... --step ... --answer ...`.
- TDD: тесты писались первыми; итого 73 теста в проекте.

**Живой smoke (GigaChat-2-Max):** задача на скорость решена верно (1.2 с, 312 токенов); ошибка ученика «7 1/8 + 2 5/8 = 9 5/8» найдена детерминированно (валидатор: посчитано 39/4, написано 77/8) — ядро «LLM решает, SymPy проверяет» работает.

**Отложено осознанно:** function calling `calc()` в Solver (арх. §4) — добавим, если у эталонов появятся арифметические ошибки на реальных заданиях; Comparator/Classifier — неделя 3.

## 2026-09-04 — Сессия 9 (продолжение): живой тест бота в MAX

Токен получен, бот «Домашка ИИ» запущен (`uv run python -m hwcheck bot`, long polling). Живой тест вскрыл пять проблем, все закрыты через TDD (149 тестов):

1. **TLS к platform-api2.max.ru**: сертификат НУЦ Минцифры. `MAX_CA_BUNDLE` (тот же корень, что для GigaChat) добавляется к certifi, а не заменяет его — медиа могут отдаваться с хостов под публичными CA. `certifi` объявлен прямой зависимостью.
2. **Пересланные фото**: MAX кладёт вложения в `message.link.message.attachments`, body пустой. Модель `MaxLink`, `image_urls` читает и оттуда.
3. **Альбом «учебник + тетрадь»**: обрабатывалось только первое фото; страница учебника давала 7 вызовов солвера и 7 «не уверен». Новый модуль `bot/pages.py`: роль страницы детерминированно по результату vision (есть «Ответ:» или строк с работой не меньше, чем условий → тетрадь), условия учебника хранятся в `ChatState.textbook_tasks` (тетрадь может прийти следующим сообщением), проверяются только задания тетради, до 4 фото за сообщение.
4. **Номер рукописью читается ненадёжно** («№19» → 29): сопоставление условия по баллам — номер 2 балла, каждое общее число условия и записи ученика (220, 180, 700) — 1, порог 2; при совпадении по содержанию номер берётся из учебника.
5. **Школьная запись ответа**: «Ответ: 300 человек отдыхали в августе», «= 300 (чел.) - отдохнуло в августе» не парсились → uncertain. `mathparse`: метка «Ответ:», скобки-единицы, ведущее число — только если в хвосте нет других чисел («2 км 300 м» по-прежнему uncertain, а не ложная ошибка); в строке шага правило применяется лишь к результату после последнего «=».

**Итог живого прогона того же альбома**: учебник (7 заданий) + тетрадь (№19) → один вызов солвера по печатному условию → **correct** (700 − (220 + 180) = 300). Токены: ~4.3k учебник + ~2.6k тетрадь на vision, солвер из кэша.

**По ревью (code-reviewer, 3 HIGH — закрыты):** роль страницы больше не считается по числу строк (структуризатор может сложить печатные выражения в строки каждого задания) — тетрадь определяется по «Ответ:» или по вычисленному равенству «число = число» (валидатор), страница без условий со строками — тоже тетрадь; сбой одного фото (сеть/vision) не теряет остальные; условия учебника живут 60 минут (`textbook_saved_at`, `TEXTBOOK_TTL_S`); при >4 фото бот говорит, что взял первые четыре. Второе ревью (парсер, 2 HIGH — закрыты): «Ответ -5» терял минус (дефис перед цифрой — знак, не разделитель); сопоставление по содержанию считает только отличительные числа (от двух цифр, встречаются в одном условии страницы), порог 2, одно условие достаётся одному заданию тетради (кроме точного номера); запятая/точка в десятичных не различаются. 161 тест.

**Инструменты/окружение**: Chromium блокирует фрейм канваса Claude Design при Clash Verge в TUN-режиме с fake-ip (198.18.x.x считается локальной сетью) — обходится локальными файлами. `TaskStop` фонового `uv run` не убивает дочерний python — добивать по командной строке.

**Открыто**: калибровка роли страницы на реальных фото (событие `vision_recognized.role` пишется в журнал — есть на чём тюнить); диалог тьютора живьём ещё не гонялся; логировать распознанную страницу в dev-режиме, чтобы не перегонять vision при разборе.
